# Module card: api-front-office (P-615)
The firm's front office: public booking and retainer agreements, with their files. Read this before editing these files; update it in the same PR when an entry point, invariant, table or test below changes (or say `Card unchanged: <reason>` in the PR body).

**Purpose.** `sales/` leads (FO-2): the one arrival path, the public web-form door, the lead inbox and its changes, the open-hours wait (`open-minutes.ts`); `duplicates/` the one duplicate match (FO-9a: email, E.164 phone, similar name; `phone.ts` normalises with libphonenumber-js); `booking/` the booking service, its public door, slots, calendar files (`ics.ts`) and self-service tokens; `retainers/` retainer and consultation agreements from templates (`docx.ts`, `placeholders.ts`); `render/gotenberg.ts` Word to PDF (the real DocumentPdfPort on Gotenberg's LibreOffice route, PF-Fp; not wired yet, FO-5p part 2 wires `pdfFromEnv`); `signing/` (FO-6) the vendor-neutral SigningPort, its fake and its contract (`tests/check_fo6_signing_port.ts`; no route yet: the API is the row's next part, the vendor adapter FO-6v); `files.ts` the real FilesPort with short-lived checked download links; `compliance/identity/` the client identity check (FO-13i, Code s. 24(2)(a)); `*-seed.ts` Sample seeds; `people/fo-person-port.ts` (FO-1p) the FoPersonPort adapter, bound as `FO_PERSON_PORT`: the one way the case side gets a case client's fo_person (PERSON) or fo_company (COMPANY), in the caller's transaction, never a same-email person reused (BR-2), a `prospectId` returning that prospect's own party, FO-1a's seed first for a firm with no sales setup row, one audit line of ids only.
**Owner area.** front-office module rows FO-* (Unconfirmed: no lane map in code).
**Entry points.** `/api/public/forms/:token` (open read) and `POST …/submissions` (the public door, FO-2); `/api/front-office`: the leads and prospects routes (FO-2 parts 1-3, FO-2b, FO-4sf), listed in `sales/README.md`; FO-9a: `POST duplicates/check` (key show; reads only); `GET retainer-templates`, `POST retainer-templates/:id/versions`, `POST prospects/:id/retainers`, `POST retainers/:id/send`, `POST retainers/:id/signed-offline`, `POST retainers/:id/download-link`, `GET files/:token`; FO-13i: `POST people/:personId/identity-checks` (key `agent/identity-check:record`, multipart, optional `copy`; a required `requestId` uuid is the check's id: a replay returns it, other details → 409 `REQUEST_REUSED`), `GET people/:personId/identity-checks` (key `agent/prospect:show`), `POST identity-checks/:id/copy/download-link` and `GET identity-copies/:token` (key `agent/document:show`); `POST retainers/:id/send` answers `warnings` ("No identity check is recorded for <signer>.", never a block); the booking page's public controller under `/api/public` (FO-3, FO-3pa): `GET firms/:firmKey/book` (the list), `GET firms/:firmKey/book/:slug/slots`, `POST …/bookings`, `GET bookings/:token`, `GET bookings/:token/slots`, `GET bookings/:token/ics`, `POST bookings/:token/reschedule`, `POST bookings/:token/cancel` (optional `reason`); the staff booking routes (`booking/staff.controller.ts`, FO-3sr) `POST bookings`, `POST bookings/:id/reschedule`, `POST bookings/:id/cancel` (keys create, edit), `GET bookings`, `GET bookings/attendance-due` (key list), `GET bookings/:id`, `POST bookings/:id/attendance` (any staff: the host's own, the service checks the rest and answers 404). FO-3sa: create and reschedule take any time; a time with warnings answers 409 `WARNINGS` and saves nothing until the body carries `bookAnyway: true` and `acceptedWarnings` (the codes shown); create takes `hostStaffId` (an active host of the type). `files.ts` `LocalFiles` (FilesPort): `put`, `get`, `exists`, and `delete` (PF-Fd: the caller asked `LegalHoldPort.isHeld` and committed the record first; removes the bytes inside the firm's folder only, keeps a tombstone in the `.meta` file, so the key is retired and a later `put` of it is refused).

**Invariants (set by).**
- Every public read is marked open on the read guard (OpenRead, P-348 (4)); the door's own protections live in the service.
- Every public miss (unknown firm, hidden, retired or unknown type, bad or voided link) is the one identical not-found; public answers carry no ids (FO-3pa, BR-2).
- A type's `allowReschedule` and `allowCancel` are read inside the change's transaction, after the row lock; a booker's cancel reason is kept on the booking (`cancel_reason`, at most 500, only when CANCELLED), never in the audit entry (FO-3pa, Lead B rev 16.30).
- A self-service token is `<selector>.<verifier>`: looked up by id, verifier checked (FO-3, BR-10).
- A web-form post makes nothing on a refusal; its answer never says whether the person is known; a stamp not ours asks for a reload (FO-2, AG-2-49).
- Sales (leads and prospects): the change, visibility, company and stage-move rules in `sales/README.md` (FO-2, FO-2v, FO-2b, FO-2 part 3).
- Word to PDF never blocks a send: `toPdf` never throws, a failure is "no PDF" and the `.docx` is kept (`withPdf`); over 10 MB or not a zip is refused before sending; only `/forms/libreoffice/convert` is called, no redirect followed; CI and the demo use `fakePdf` (PF-Fp, gate entry 17).
- The duplicate check only reads (no row, link or audit line); it names a match only to a caller who may open it (a visible lead of the person, or a company the caller sees), any other is a count with the fixed line; `fo_person.phone_e164` is kept by the database from a readable phone, never written by the app; the public form never calls the check (FO-9a, P-574 (2), AG-2-78).
- Rate limits are rolling windows per key, sized for about 100 firms in one process (P-562).
- Every file belongs to one firm and lives under the firm's own folder (FO-5, contracts §0.3). An identity check is insert-only (a correction is a new check); its copy is put first and named only in the same insert, so a failed insert leaves no record naming it; a person is seen by the leads' own-versus-all rule (one of their leads, a prospect they own, a current contact of a company prospect they own, or a retainer they represent or whose prospect they own), else 404; the document number (only its last 4 are taken), the copy's bytes, key or link never reach a log, an audit line or an event (FO-13i).
- Platform rules apply: `firmScope` on every table, platform guard on every staff route (P-559).
- The database walls these tables (PF-12): a public door finds its firm through its named bypass use (`fo.sales.web-form`, `fo.booking.public-page`, `fo.booking.self-service`), then runs as that firm (`enterFirm`).
- The attendance question (30 min after the end) is shown, not pushed: its job mails no one; the booking is the due item until a person answers (AG-4-39 rule 2, FO-3m). The answer's body is `{ outcome }` only.
- The database's no-overlap rule skips only a booking a staff member confirmed with Book anyway over an overlap (`overlapConfirmedByUserId`, FO-3sa, AG-4-63 rule 4); the public door never sets it, every writer checks overlaps under the host locks, and a move clears it unless the move is itself confirmed.

**Tables.** foLead, foPerson, foArrivalReceipt, foLeadAttribution, foNote, foReason, foService, msgConsent (through ConsentPort), foBooking, foBookingToken, foAvailability, foConsultationType, foCompany, foCompanyContact, foStageMove, foProspect, foRetainer, foRetainerTemplate, foRetainerVersion, foSalesSetup, foStage, foWebForm, foIdentityCheck, platformFirm, platformStaff, moduleEvent.

**Do not.**
- Serve a file without a checked short-lived link, or from another firm's folder.
- Open a staff route without the platform guard.
- Let the signing provider email anyone: SigningPort takes no address and no vendor-email option (FO-6, P-563).
- Store a token's verifier unhashed (it is kept as a SHA-256, `hashVerifier` in tokens.ts).

**Booking settings and the consult record (FO-3a parts 1a, 2a).** Kept in a section of its own so the one-line lists above merge by themselves.
- Entry points: `booking/settings/types.controller.ts` under `/api/front-office`: `GET booking-types`, `GET booking-types/:id`, `GET booking-types/:id/preview?from&to&tz` (key `agent/booking-event-type:list`); `POST booking-types`, `PATCH booking-types/:id` (with `version`), `POST booking-types/:id/duplicate`, `POST booking-types/:id/switch-off|switch-on`, `DELETE booking-types/:id` (soft) (key `…:edit`). 2a: `booking/consult/controller.ts` `GET|PUT bookings/:id/consult-record` (AnyStaff: the booking's host, or `agent/booking:edit`, checked by the service; GET with no record → 404 `NO_RECORD` with `bookedMinutes`; PUT creates or replaces); `ports/consult-record.ts` `ConsultRecordPort.read(tx, firmId, recordId)` (shared contract, P-423; adapter `booking/consult/port.ts`) for FO-5's retainer draft (FO-5cr). Table foConsultRecord (`prisma/schema/front-office-consult.prisma`). Invariant: A deleted booking type (`deletedAt`) is hidden everywhere and never bookable (public door, public list, staff create read `active: true, deletedAt: null`); its bookings stay readable and changeable by id or link; its slug is free again (unique among not-deleted rows). A type edit needs the version read (409 otherwise) and never changes a booking (FO-3a). A consult record opens only on an Attended booking (COMPLETED; else 409, nothing saved), a save names the version it read (else 409 `STALE_VERSION`), one per booking keyed on (firm_id, booking_id); a later No-show keeps it (`attendanceChanged: "NO_SHOW"`); a fee is minor units with CAD or USD, never a currency alone; `nextSteps` are the server's, per viewer (retainer steps need `agent/retainer:draft`, Close lead `agent/prospect:lose`); a save sends nothing and writes one audit line of facts, never the notes' text (FO-3a 2a). Tests: `tests/check_fo3a_booking_types.ts`, `tests/check_fo3a2_consult_record.ts`.
