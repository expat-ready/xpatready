## Findings

1. **Important: test proves nothing (claim not proved).** `web/src/modules/system/privacy/holds.ts:16` and `tests/check_pf21rs_browser.ts:84`, `:462`, `:468`.
   * The round-1 commit (e25fa6e451) claims review M1 is fixed for "missing dates or reason". Review M1's fix asked for the words to be asserted.
   * The date branch of `holdDraftErrors` (`datesNeeded`, `datesOrder`) is asserted nowhere: neither the unit block at `:84` nor the browser fail lines at `:462` and `:468` cover it. It could regress, or never have worked, and every check would stay green.
   * **Fix:** add to the "B2 P pass/fail" block:
     * `holdDraftErrors({...DATE_RANGE, from: "", to: ""}, true, true)` gives `from: HOLD_COPY.datesNeeded`;
     * `from: "2026-11-20", to: "2026-11-01"` gives `to: HOLD_COPY.datesOrder`;
     * equal dates give no date error;
     * the same draft with `advanced = false` gives no date error.
   * Each should fail if the branch is removed.
2. **Nit: wrong status tone.** `holds-page.tsx:67` → `:124` → `:94`.
   * A release refused as "already released" (409) is shown through `setDone`, so it appears in the green `text-text-ok` success line. A conflict reads as a success.
   * **Fix:** give `onStale` its own neutral or warning line (or a `tone` on `done`).
3. **Nit: one missing field reported at a time.** `holds.ts:16`.
   * With both dates empty, only `from` gets `datesNeeded`. After the person fills it, a second submit is needed to learn that `to` is missing too.
   * **Fix:** set `out.from` and `out.to` separately, each when empty.
4. **Nit: stale hint wording.** `holds.ts:79`.
   * `idHint` says the id is "not checked here", but the dialog now refuses a malformed id (`holds.ts:15`). What it does not check is whether the record exists.
   * **Fix:** "...; its format is checked, not whether the record exists."
5. **Pre-existing: missing ownership check.** `api/src/platform/register/holds/service.ts:52-53` (`PlaceBody` / `ScopeBody`).
   * A PERSON or CASE hold accepts any well-formed UUID. The API does not check that the record exists or belongs to the named firm, so a pasted id from another firm, or a typo, places a hold that protects nothing, and it is listed as Active.
   * This is the review's D2 note (concept M4) and is not caused by this diff.
   * Log it for a later runtime row.

The PR adds a feature; it is not a fix PR, so the root-cause question does not apply.
