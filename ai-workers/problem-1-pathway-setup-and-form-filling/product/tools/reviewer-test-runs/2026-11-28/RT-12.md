# Review: PR #3658, FO-7s3a part 1 (Record payment, Payments list, payment detail; trust off). Round 1, full review

2 Important, 2 Nit, 2 Pre-existing

This PR is risky under §5 because it writes money: it records payments and keeps extra as credit. So both Important findings must be fixed, or resolved with a one-line reason I accept, before Approve.

Paths below are relative to `ai-workers/problem-1-pathway-setup-and-form-filling/prototype/studio/`. Line numbers are as of 0f68e5283b9a30b5b9394d6547ea8dbde5fd7b61.

## Important

**1. The panel offers "Keep as credit" on an uncleared cheque, and the server always refuses it.** Bug class: action offered that always fails.
- Where: `web/src/modules/client-money/payments/record-payment.tsx:80`. The panel works out `waiting` only from `done.extra.waitingMinor > 0 && choices.includes("KEEP_AS_CREDIT")`.
- Why it fails: the record answer (FO-7b `paymentView`, `api/src/client-money/invoices/money.ts:248`) lists `["REFUND","KEEP_AS_CREDIT"]` without checking whether the payment has cleared. But `POST …/payments/:id/extra` refuses an uncleared payment with 409 NOT_CLEARED (`api/src/client-money/invoices/refunds.ts`, `choose`, the "This cheque is not cleared yet" line).
- What the user sees: record a cheque for more than the balance due. The panel shows "Not yet cleared" and also "Choose what happens to it" with a Keep as credit button. Every press ends in "Not saved". The cheque is the method of this PR's own main walk (W1).
- Why the test misses it: DW3 (`tests/check_fo7s3a_payments_trust_browser.ts:240`) overpays only by BANK_TRANSFER.
- Fix: add `&& done.cleared` to `waiting`. For an uncleared payment, show the same words as the server: "its extra waits until it clears". Add a check line that overpays by CHEQUE and asserts that no `[data-pay-keep]` button appears.

**2. "Keep as credit" on the payment detail page is a new money write that no test covers.** Bug class: test proves nothing.
- Where: `web/src/modules/client-money/payments/detail.tsx:31-35,45`. This is a separate code path that posts `KEEP_AS_CREDIT` and has its own message and its own refresh.
- Why it counts: the header claims this action, but the browser check opens the detail page only for facts, C5 and screen sizes (`tests/check_fo7s3a_payments_trust_browser.ts:266,275,295`). Nothing clicks `[data-action="KEEP_AS_CREDIT"]`. DW3 tests the panel's Keep, not this one. If this path broke, no line in the check would fail.
- Fix: add a check line. Record an overpayment, close the panel without choosing, open `/money/payments/:id` and click Keep. Then assert: one KEPT `money_credit_entry` row for the payment, the "kept as credit" notice, the button gone after the refresh, and a second POST answering NOTHING_WAITING.

## Nit

Fix: use `x.field("amountMinor")`, the same as the other fields.

## Pre-existing (log for a later row; do not fix in this PR)
1. Bug class: inconsistent permission/state rule. `api/src/client-money/invoices/money.ts:248`: `PaymentView.extra.choices` offers REFUND and KEEP_AS_CREDIT for an uncleared cheque. `Refunds.standing` / `choose` in `invoices/refunds.ts` refuse both. The record answer and the payment read disagree on what may be offered. This is the server-side root of Important 1. Fix in FO-7b: build `choices` from `standing()`, or gate it on `p.cleared`.
2. Bug class: weak idempotency match. `api/src/client-money/invoices/money.ts:98`: a reused key replays when invoice, amount, method and destination account (`receivedInto`) match. It ignores `reference` and `receivedOn`, so a retry with a different date or reference is answered "replayed", as success, and the change is silently lost. This PR's panel freezes the fields after "No answer yet", so this PR does not reach it. Another caller can. Fix: compare `reference` and the received day too, and answer KEY_USED when they differ.
   - Related, also in FO-7b (`money.ts:91` with `facts.ts:14` `dayOf` = UTC): "the future" means after the UTC day. A firm east of UTC, such as one in IST, cannot record a payment on its own today between 00:00 and 05:30 local time. The panel's `latestDay` follows the same UTC limit.
