## Findings

**1. Important: a test that fails on later changes (it reads the git state, not the database).** `prototype/studio/tests/check_css1_index.ts:580-582`
The DW4 "answer-write sites unchanged" check runs `git merge-base HEAD origin/main` and then `git diff --stat <base> -- api/src/**/*.ts`, and fails unless the result is empty. The brief scoped this to "in this part" (CS-S1.md:31), but the check is now a permanent assertion in a suite that keeps running after the merge. In CI the head is the test merge on origin/main (ci.yml:234-240, `pr-base.sh`), and the merge queue runs every suite (`run-suites.sh --skip-quarantined`). So any later PR or batch that edits any `api/src/**/*.ts` file turns this suite red, even though the index is fine. It also fails in any copy that has no `origin/main` (`base === ""` counts as a fail), and in a builder copy with uncommitted API edits. CS-S1 part 2 itself has to add `api/src/search/party-search.ts`, so it will trip this check.
Fix: take the git check out of the suite. Prove "no write site changes" once, in this PR's evidence, or as a property of the database: for example, the answer-write paths never name `case_party_index`, checked by `git grep -n case_party_index -- 'api/src/**/*.ts'` returning nothing outside the part 2 read path. Or skip the check when the diff touches only files other than answer-write sites.

**2. Important: an answer key missing from the index (requirement not met, untested).** `prisma/migrations/20261117004500_css1_case_party_index/migration.sql:190-191, 209-215, 238-243`
The brief asks the builder to list "the exact keys from the answer-key families" (CS-S1.md:8), and AG-7-75 rule 3 requires search by phone. The answer-key families on main store the principal's phone as `person.telephone_number`, as a `{country_code, number}` object:
- `samples/answer-key-families.json:46`: the principal "mother", `person.telephone_number` `{ "country_code": "91", "number": "9800000001" }`
- `samples/sample-family-imm5257.json:54`: the checkpoint loader's Sample family
- `engine/runtime/team.ts:117-129`: `person.telephone_number` is a phone fact in its own right

The refresh reads only `person.phone_number` (plus `person.phone_country_code`), and the two trigger WHEN lists leave `person.telephone_number` out. Every IMM 5257 (visitor visa) client therefore gets `phone_e164` null, and the phone search in part 2 can never find them. No DW case covers this key.
Fix: add `person.telephone_number` to the key list in `case_party_index_refresh`, in both triggers' WHEN clauses and in the header. Read it as `coalesce(person.phone_number, person.telephone_number)`, through the same object, string and number branches. Add a DW1 pass case (a principal with `person.telephone_number` `{country_code:"91", number:"9800000001"}` gives `+919800000001`) and a fail case. Check `person.given_name` and `person.full_name` in the families in the same pass, and list in the PR why each one is in or out.

**3. Nit: the header and the function disagree.** `migration.sql:43` vs `migration.sql:146-150, 153`
The header says a phone is null "outside E.164's 15 digits". The function also refuses numbers under 7 digits, a subscriber part under 4 digits, all zeros and a country code that starts with 0. Make the header line match the function's comment, or have it point to that comment.
