## Important

**1. The migration needs PostgreSQL 18, but the supported setup path still starts and keeps copies on 17.** Bug class: unguarded platform requirement.
`prisma/migrations/20261119144500_csnk1_field_name_key/migration.sql:22` uses `COLLATE pg_unicode_fast`, which first appears in PostgreSQL 18. Line 18 says so: "Needs PostgreSQL 18 (… the Mac, cloud and CI copies run 18)".
`studio/tools/new-machine.sh` (B168, any founder's Mac) still accepts any major of 16 or newer:
- `find_pg` lines 66 and 72 accept `-ge 16`, and line 69 tries `postgresql@17` in turn.
- An existing cluster stays on the major it was made with (lines 111 and 133, `find_pg "$(cat PG_VERSION)"`).

So a copy that already runs on 17, or a Mac where 17 is the newest install, fails `prisma migrate deploy` on this migration with "collation pg_unicode_fast does not exist". Prisma then records a failed migration (P3009), which blocks every later deploy, and the Studio does not start. Before this PR, 17 worked: main needed only `pg_c_utf8`, which is 17+.
Fix, in this PR:
- Raise new-machine.sh's floor to 18: change the `-ge 16` checks to 18, drop `@17`/`@16` from the probe list, update the messages at lines 138 and 144, and stop on an existing cluster older than 18 with a clear upgrade message.
- At the top of the migration, add a guard that fails with a readable message: `DO $$ BEGIN IF current_setting('server_version_num')::int < 180000 THEN RAISE EXCEPTION 'CS-NK1 needs PostgreSQL 18 (pg_unicode_fast)'; END IF; END $$;`
- Add a case for the new floor to `product/tools/check-new-machine.sh`.

**2. The new suite fails as soon as any later migration merges.** Bug class: test coupled to unrelated state.
`studio/tests/check_csnk1_name_key.ts:88` asserts `all[all.length - 1] === NEW` ("this row's migration is the newest on the branch"). `run-suites.sh` runs every `tests/check_*` file in the CI shards. The first PR that adds any migration after 20261119144500 will therefore turn this suite red even though it changed nothing here, and main breaks. The check proves nothing that the test needs: "bare" already selects `d < NEW`, and DW4 applies NEW by path.
Fix: remove the assertion, or replace it with `all.includes(NEW) && OLD < NEW`.

## Nit

**3. The DW4 fail check compares against the wrong value.** Bug class: test proves less than it says.
`check_csnk1_name_key.ts:151-152`: the label says the stored keys "differ from normalizeLabel", but the query compares `name_key` with an ASCII-only strip, `lower(regexp_replace(label,'[^A-Za-z0-9]+','','g'))`. Fix: read the rows and compare them with `normalizeLabel(label)` in TypeScript, as the DW4 pass check at lines 160-161 already does.

**4. A tautology in DW3.** Bug class: test proves nothing (part of a condition).
`check_csnk1_name_key.ts:118`: `accepted === PAIRS.length` is always true, because it is the `.length` of a `map`. A refusal only shows up as a thrown error reaching the outer catch. The `count(*)` half carries the check. Fix: drop `accepted` and keep the count, or catch the error for each pair and report which pair was refused.

## Pre-existing

**5. new-machine.sh has been out of step with main since the PostgreSQL 17 requirement.** Bug class: stale version floor.
`tools/new-machine.sh:66,72,138,144` say "16 or newer", but main has needed 17+ since `20261115042334_fo7a_client_money_tables/migration.sql:526` (`pg_c_utf8`). A version-16 copy already fails there. This PR did not cause that; it raises the gap to 17 (finding 1). Log it for a later row if finding 1 is fixed without touching the 16 path.
