## Proposed finding (needs a QA number; code read, not yet probed at runtime)
**Gap · Minor (proposed): when a move hands the booking to another host, the first host's calendar keeps the old event.**
* `service.ts:569-571` can give the moved booking a different `staffId`: the first free host when the original host is not free at the new time.
* The "moved" mail goes only to the current host (`:661-663`, `to: host.email` for `b.staffId`). The original host never gets a METHOD:CANCEL.
* The new host gets a REQUEST with a SEQUENCE above 0 for an event they never had, which calendars accept.
* Expected: on a host change, the original host gets a METHOD:CANCEL for the UID, and the new host gets the REQUEST.
* It does not hold R1.40's verdict, because the line is worded for the booker's event (the reader agrees). It does affect a staff member's calendar.
* Owner: front office (FO-3 booking).
* Not logged in `BUGS.md` yet: qa 10's number block (QA-520 to QA-529) is used up. qa 7 used QA-522 to QA-528 inside it.

A second note from the reader, not a defect: if a booking changes again before its mail goes out, the older mail is skipped (`runMail`, `:650`). The newest invite still wins in a calendar.
