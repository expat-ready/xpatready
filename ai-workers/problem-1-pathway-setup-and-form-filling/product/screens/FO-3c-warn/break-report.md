## Findings

**F1 (Major): after Attended the warning and the panel give opposite advice, and both are wrong for one state.** The words before Attended also hide that saving Attended stops the client signing.
- Repro (scratch X1): an agreement is SENT, then the booking is marked Attended. The Attended answer says "this booking can no longer be signed for or rescheduled" (gate.ts:41). The client's link now answers 404, because `openAs` checks `bookingActive` (consultation-agreement/service.ts:403). The booking panel still says "Not signed yet. The client signs from the link in their email, then <signatory> signs." (agreement.tsx:48). That is false: the link is dead.
- Repro (scratch X2): the client signs (CLIENT_SIGNED), then the booking is marked Attended. The answer, and the consult record's notice (consult-record.tsx:101), say the agreement "can no longer be signed for". In fact `hostLink` still answers 200 (service.ts:481, which has no booking-status check). The firm's signature is applied, the agreement becomes SIGNED and the warning goes away. Meanwhile the signatory's "Needs you" item disappears once the booking is Attended (`needsYou` only lists SCHEDULED/RESCHEDULED bookings, service.ts ~365): X2 shows `{"items":[]}`. So the one person who can still finish the signature is told it can't be done and gets no prompt.
- Before Attended, WARN_WORDS (gate.ts:39) and the panel say "The client signs from the link in their email… Attended and the consult record can still be saved". They never say that saving Attended ends the client's link. Under warn-never-block, "meet, then sign" is now the normal path, and it silently becomes "make a new booking".
- Expected: one true message per state. Attended plus SENT/VIEWED: the client can no longer sign this one. Attended plus CLIENT_SIGNED: the firm can still sign. Before Attended: say that Attended closes the client's link.

**F2 (Minor): leak — the consult record hands the agreement's id and state to someone the agreement read refuses.**
- Repro (scratch X9): a CASE_OFFICER with "everyone sees all" off, who doesn't own the lead. `staffBooking` → 404, agreement `by-booking` → 404, Attended → 404. But `GET bookings/:id/consult-record` → 200, now including `agreementWarning.agreementId` and the unsigned state, and on a no-agreement booking the cause words too (e.g. "the client has no email address on file").
- Cause: `ConsultRecordService.booking` accepts any holder of `agent/booking:edit` without the record rule (consult/service.ts:179). That gap already existed for the record itself. This change carries it over to the consultation agreement, which FO-3vr hides on purpose (suite P5). The data stays inside the same firm. Other firms get 404 (held, below).

**F3 (Minor): the warning is read after the commit, so a failed read turns a saved change into a 500. A retry of the record then says someone else saved it.**
- Repro (scratch X6): `$queryRawUnsafe` is made to fail outside the transaction. `PUT consult-record` → 500 "connection lost", but the database already holds the new version (2, 45 min). Retrying the same save → 409 STALE_VERSION "Someone else saved this record". That's false: the user saved it themselves. Attended → 500 while the booking is already COMPLETED and `booking.completed` is in the outbox (retrying is harmless: the second answer is 200).
- Where: consult/service.ts:160, booking/service.ts:463. Expected: a failed warning read gives a null or "unknown" warning, never a 500 after a commit.

**F4 (Minor): the consult record shows no warning before its first save.** That first save is the moment the warning is for. `GET` answers 404 NO_RECORD without `agreementWarning` (consult/service.ts:118), and the screen only shows `record?.agreementWarning` (consult-record.tsx:78, :101). The panel's own block covers this only for viewers that `by-booking` lets through. For F2's viewer, nothing warns until after the first save.

**F5 (Minor, words): contradictory next steps.**
- Scratch X7: a meeting that is over, still Scheduled, with nothing sent. The panel `why` says "Attended and the consult record can still be saved" and then "to have it signed, reschedule the meeting to a later time" (gate.ts:71). The panel's `next` adds "If the meeting time has passed, reschedule it" (contracts/consultation-agreement-words.ts:6). Rescheduling a meeting that already took place throws away its attendance: Attended then answers too-early.
- After Attended with nothing sent, the warning reads "Attended and the consult record can still be saved… to meet the client, make a new booking" (gate.ts:78) on a booking that is already Attended. The panel drops that sentence for its own text but not for the server's `why`.

**F6 (Minor, evidence): the W4 screenshot doesn't show the shipped words.** `J-104/screenshots/w4-attended-before-signing-1440.png` shows a booking already marked Attended with "…Attended and the consult record can still be saved. This booking is already marked Attended…". The same commit (06a9cfd29) then made agreement.tsx:48 drop that sentence for COMPLETED. The screenshot was taken before that edit, so it isn't evidence for the code as shipped.

## What held
- **Permissions (Attended):** firm B → 404. A list-only colleague who doesn't host → 403 MISSING_PERMISSION, and the booking stays SCHEDULED. A colleague hidden by the record rule → 404. The suite's W3 also passes.
- **Permissions (consult record):** another firm → 404. List-only → 403. A malformed id (`x' or 1=1`) → 404. Removing the 409 gave nobody new write rights: who may write is decided before the transaction, exactly as before.
- **Money path:** `booking.completed` has no consumer anywhere in api/src. The only module_event readers of booking events are live.ts and service.ts:113, and both take only `booking.scheduled`/`rescheduled`. A booking carries no price or charge, and the consult record's `quotedFee` is only a quote. Nothing bills at Attended.
- **Other firms' data:** every join in `unsigned()`/`missingCauses()` stays inside `b.firm_id`. The warning never names another firm's agreement.
- **Warning per state:** SIGNED (X2, after the firm signed) and SIGNED_OFFLINE (suite W2) → null. Type switched off → null (X4). Type soft-deleted → GET still 200 and still warns (no throw; the foreign key is RESTRICT, so a hard delete can't happen). No-show answer → null. Several agreements, with any one signed → null (suite B10). Cancelled → no warning.
- **Races:** Attended still takes the booking's row lock. A second Attended returns the same booking plus the current warning. The warning is read after the commit, so it can only be fresher, never wrong about the saved state (apart from F3's failure path).
- **Words:** no warning, panel or settings text names a regulator or statute (the statute appears only in comments and the template checklist, which this change doesn't touch). Nothing in the changed product text still says "cannot start" or "wait". The client email says the meeting stays booked.
