## What held
- `GET /handlers` (as Owner and as Case Manager) lists only the Owner, a Case Manager and an Admin. It leaves out: Read-only, Case Officer, Billing and finance, a person with no role, SUSPENDED, DEACTIVATED. A Case Officer calling it → 403 MISSING_PERMISSION.
- Recording a complaint with any of those people as handler → 422 at `handlerStaffId`, and nothing is written. Admin as handler → 201.
- Role change mid-session, same token: demoted → 403 on acknowledge and on a NOTE; GET 200; the complaint stays in their list. Re-granted CASE_MANAGER on top of READ_ONLY → acknowledge 200. Several grants (READ_ONLY + CASE_OFFICER, CASE_MANAGER ended) → 403. Keys are read from current grants on every request.
- A grant cannot be given a future end date (`platform_role_grant_ended_check` refuses it), so "ends tomorrow" cannot pass as current.
- Handler change: to an upper-case form of the current handler's id → 422 "this person already handles it" (the ids are folded to lower case). To a person with READ_ONLY + CASE_OFFICER → 422. An upper-case complaint id → 200 for the Owner.
- Idempotent replay: (a) the same key and body after the handler lost the key → 200, the same id, nothing written (1 row for the key). (b) A request first refused 422 (Read-only handler), replayed with the same key after that person was made Case Manager → 201: the refusal had stored nothing.
- Existence leaks: a person who neither reads nor handles a complaint gets 404, the same as for an unknown id. A Case Manager who is not the handler gets 404 on `/:id/handler`. A handler without the key gets 403 only on their own complaint, which they can read anyway.
- Web picker: the record and handler-change panels both fill from `GET /handlers`, so they offer no one the API refuses.

Note: the 403 in M1 and m2 is the API holding the line. M1 is the screen not following it.
