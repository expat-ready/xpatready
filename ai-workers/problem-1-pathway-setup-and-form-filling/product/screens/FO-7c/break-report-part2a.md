Method: the PR's own harness (`tests/check_fo7c_pay_link.ts`) copied to a scratch folder: a scratch database with every migration, a Nest app with PF-4's guard and PF-12's walls, on an ephemeral port (never :4400), plus the code read. ## Verdict: **Changes** (no Blocker, 2 Major, 4 Minor)

## Major

**M1. Making a new link (or renaming the firm) gives a server error at "Pay" on the real rail for 24 h, and on the fake the new link gets the old link's Stripe session.**
Steps: issue a 1,000.00 invoice; `POST …/pay-link` → T1; `POST /api/public/pay/T1/session` (200); `POST …/pay-link` again → T2 (T1 replaced, as designed); `POST /api/public/pay/T2/session`.
What happened: the idempotency key is `fo7c-pay-<invoice>-<due>-<payments>` (pay.ts:149), so it is the same for both calls, but `successUrl`/`cancelUrl` now hold T2 (pay.ts:146). Stripe refuses a key that comes back with other parameters (`idempotency_error`, 400). On the Stripe adapter both calls sent key `fo7c-pay-0ebd…-100000-0` and the second got the 400 back. `stripe-rail.ts:44-52` maps nothing, and pay.ts:152 rethrows anything that is not RailRefused or RailAccountGone, so the app's filter answers a 500 "Something went wrong" (main.ts:231-232). The client cannot pay by card and is not shown the offline details. The same happens when the firm's `operating_name` changes between two Pay clicks (the description at pay.ts:148 changes): scratch case 6c gave 200, then 400 idempotency_error. On the fake rail (`once()` ignores parameters, rail.ts:166), T2's Pay returns T1's session, whose success and cancel URLs point at the replaced link, so after paying the client lands on "This payment link does not work". The fake hides the bug, so the suite stays green.
Should: the key changes whenever any parameter can change (at least the link's token hash, or the stored link's version, and the description), or the URLs and description come out of the keyed parameters. A test should prove a new link's session after an old one on a rail that compares parameters, as Stripe does.

**M2. A Stripe page handed out earlier stays payable for the old amount after the invoice changes. One invoice took 1,600.00 of card money for 1,000.00 billed.**
Steps (fake rail, ACTIVE account): a 1,000.00 invoice, link T; `POST …/session` → `cs_fake_3` for 100000; staff record 400.00 by e-Transfer; `POST …/session` → `cs_fake_4` for 60000 under a new key. Both sessions stay live: `rail.succeed` on both charged 100000 + 60000 = **160000** against a total of 100000 (scratch cases 4 and 4b). The same holds after the link is replaced, credited, written off or paid in full. The door then says LINK_NOT_WORKING, but the hosted page already handed out still takes the card. `createHostedPayment` sends no `expires_at` (stripe-rail.ts:46-49; Stripe's default is 24 h), and the rail has no call to expire a session.
Also seen once in four runs (not deterministic): two tabs asking for a session while an offline 250.00 payment landed. One tab got a session for **100000 under key `…-100000-1`**, the full amount with the payment already counted. The due amount (pay.ts:103) and the payment count (pay.ts:145) are separate reads with no shared snapshot, so a session can be made for more than is due at that moment.
Should: limit the window (a short `expires_at`, and expire the open session when a new link is made, the invoice is settled or the amount changes; this needs a rail call), and read the amount and the count in one snapshot. Part 2b must take a card payment above the due amount as `extraMinor`, never as fees earned. That is a client-money question; legal reading Unconfirmed: no counsel. At least one of these should be in 2a before Stripe test mode goes live.

## Minor

**m1. The "processor no longer knows the account" fix (commit d4b1185d7) only works on the fake.** The fake throws `RailAccountGone` from `createHostedPayment` (rail.ts:167/176). The Stripe adapter does not map Stripe's errors there (stripe-rail.ts:44-52; compare readAccount at :36-38). On the mocked Stripe adapter, a revoked account (403 "does not have access to account"), `account_invalid` (400) and "cannot currently make live charges" (400) each become a 500 in the app, not the 409 CARD_NOT_OFFERED with the offline details. This is the AG-16-17 path the PR claims; it is only reached when the account row is stale. Should: map these errors to RailAccountGone or RailRefused in the adapter, with a test on a mocked fetch.
**m2. The limiter's memory is not capped within a minute.** Every request adds a `t|ip|token` key before any check (routes.ts:71), including requests already answered 429. MAX_KEYS (routes.ts:52) only starts a sweep of keys that are already stale. 20,000 distinct junk tokens from one address added about 11 MB of heap (about 560 bytes each), so memory grows with request rate × 60 s. No `trust proxy` is set, so behind a proxy every client shares one address and one miss budget. Valid links are not affected (13b: a fresh link answered 200/200 after the ceiling). Same design as the signing door.
**m3. "No body" is not enforced for every content type.** `text/plain` `{"amountMinor":5}` → 200, a new link is made and the earlier one stops working. JSON `{}` 200, `{amountMinor}` 422, `[]` 422, form-urlencoded 422, `null` 400, 2 MB 413. Nothing is charged, but the route's comment says any field is refused (routes.ts:45).
**m4. The suite never runs the real C5 wiring.** It stubs `scopeOf` with "ALL" or `failClosed`. With `PgMoneyVisibility` (as `features/client-money-card.ts` wires it), the out-of-scope officer → 404 (good), but the Owner also got 404 for an invoice with no case whose person is not a prospect subject. That is FO-7b's party rule, not this part's. A pass case on the real scope would prove the wiring.

## What held
* Tampered tokens, GET and POST: the firm part in upper case, the firm id with dashes, `..`, a trailing `.`, `.x`, `=`, a leading space, NUL, firm B's id with firm A's verifier and the reverse → the one 404 LINK_NOT_WORKING. A 20,000-character token → 431 from Node, never a 500. `%2E` decodes to the same valid token (harmless).
* GET writes nothing: 60 GETs plus 12 tampered GETs allocated **0 transaction ids** (`pg_snapshot_xmax` unchanged), added 0 audit lines and made 0 rail calls.
* A link reused after a credit, a write-off, payment in full, or a newer link → 404 on GET and POST. The newer link opens.
* Walls on making the link: firm B's Owner → 404; the narrowed officer under the real C5 scope → 404; a trust request's id → 404; a draft → 409 DRAFT; a locked firm → 409 NOT_AVAILABLE. Locked door: card not offered, the session is refused in neutral words with no "lock".
* Account states: ACTIVE with charges off, RESTRICTED (charges on or off), DISCONNECTED, PENDING, NOT_CONNECTED and no row → no card, the session 409 CARD_NOT_OFFERED, **0 rail calls**. ACTIVE but unknown to the fake rail → 409 with the offline details.
* Session amount: equal to the due amount when read, in the invoice's currency, on the firm's own `acct_…` only, metadata `firm_id` and `invoice_id` only. Part 2a wrote no CARD payment and no trust entry, and nothing can route card money to trust.
* Secrets: across 19 links, no verifier and no SHA-256 in audit lines, captured logs or the door's answers. The request log records only the route pattern (hook.ts:28-36).
* Limiter: 300 misses a minute → 429 for further misses; 30 a minute per link → 429; varying the token does not get past the miss budget from one address.
