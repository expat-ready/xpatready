## 1. Job and journey
A case officer checks a client's uploaded file without downloading it: opens it from its checklist line, reads it page by page beside the case, and goes back to the line to decide. Persona: case officer and above on the case (the download's reach, `"officer"`; AG-9-53). Requirement text: **AG-9-24** "In-app preview (PDF/image) via short-lived signed GET; every preview is access-audited"; AG-9-16 (signed GETs, never public), AG-9-20 and AG-9-55 (never an unscanned file; "Checking for viruses…", "Removed — infected file"), AG-9-32 (every read leaves a record; here the one audit trail, CS-D6). Journey: client uploads (C6.4) → scan (PF-F3) → **officer previews and accepts in the panel** (Accept: CS-D1 part 2's route; AG-09 §3.8 "accept / needs-replacing controls adjacent to the preview") → Ready to file.

## 2. Layers (STANDARDS §2)
* **Masters, links, configuration, rules:** none new. The file belongs to `case_document` (C6.4); its scan state is PF-F3's (`FilesPort.scanState`) once CS-D1 part 1 moves case files onto `FilesPort`; the "contains scripts" flag is PF-F4's byte scan (`file-type.ts`, `SCRIPTS_FLAG`), recomputed on read until contract gap 2 is ruled (brief).
* **Engine / API on main:** `GET /api/runtime/documents/:id/file` (`case-documents.ts:719-724`) already serves inline with `nosniff`, `content-security-policy: default-src 'none'; sandbox`, `private, no-store`, and writes "viewed" (`:408`). Missing against AG-9-24: the short-lived link and the "previewed" line.
* **API new (part 1, the brief's):** `POST /api/runtime/documents/:id/preview-link` → `{ url, expires_at, media_type, file_name, size_bytes, uploaded_at, scan: "CLEAN", contains_scripts }`, 409 "Checking for viruses…" / 410 "Removed — infected file" with no link (the requirement's words, m2); `GET /api/runtime/document-previews/:token` (bytes, the download's four headers), **single use** (r2, M2: the first successful GET consumes the token; a second answers 404 like an expired one). One "previewed" audit line when the link is made; with a single-use token no read goes unrecorded.
* **Screen on main:** `web/src/runtime/checklist.tsx` lists each line's current file as text ("File: passport-scan.pdf"); no viewer. `documents-drawer.tsx` `OpenFile` (`:144-161`) opens the file in a new tab as a blob (fill-from-documents only; unchanged here). The team's kit has `Panel` (`components/ui/controls.tsx:100`, right side panel, max 560 px).
* **Screen new (part 2):** `web/src/runtime/document-preview.tsx` (`DocumentPreview`, in `Panel`), PDF.js (`pdfjs-dist`, through STANDARDS §1 and P-587; P-607 S3 Q9 "PDF.js, scripts off"), one entry point in `checklist.tsx`.
* **Team's code:** not in this cloud copy (`code/` absent); the brief asks the Lead to check on the Mac whether the team already ships a PDF viewer (STANDARDS §1: prefer what the team has). Unverified here.

## 3. Business rules
* **BR-1 Only a clean file opens** (AG-9-20, AG-9-55, SA8-D2): only a clean file gets the Preview button on its line; a checking file shows "Checking for viruses…" and a removed one "Removed — infected file" there, with no button (m1; the line states are CS-D1 part 3's). If the state changes between the list and the click, the panel shows the same words, with no link made and no bytes fetched.
* **BR-2 Short-lived, single-use, nameless link** (AG-9-24, AG-9-16; 300 s from AG-09 line 426 "today 300s", m3): the link lives 5 minutes, works once (M2), is tied to the firm and the staff member who asked, and its URL holds no firm, person or file name. Bytes are fetched once into memory (`fetch` with the session header → `ArrayBuffer` for PDF.js, `Blob` URL for images, revoked on close); never an `<iframe>`, never the browser's own PDF plug-in.
* **BR-3 Nothing in the file runs** (P-607 S3 Q9, P-587): PDF.js draws to a canvas with `isEvalSupported: false`, scripting never enabled, no sandbox bundle shipped, the worker from our own origin; a version at or above the fix for CVE-2024-4367 (checked at the advisory on the day, in the gate note). A PDF flagged by PF-F4 shows "Contains scripts: opened only in the safe viewer" and still renders.
* **BR-4 Same reach as the download** (AG-9-53): who can open the download can preview; anyone else gets 404 in the download's words; a client gets whatever status the download gives a client today (measured, not changed).
* **BR-5 Every read is recorded** (AG-9-24, AG-9-32 "every read"): one "previewed" line per opening, written when the link is made; the token is single use, so no read goes unrecorded; page turns and zoom read from memory and write nothing; a refused opening writes nothing.
* **BR-6 View only** (row): page, zoom (Fit width, 100%, 200%) and rotate change the view, never the file or its record; closing forgets them.
* **BR-7 One fetch, one retry** (r2, M1): the bytes are read once into memory, so pages never need the link again. Only when that one fetch is refused as expired (a slow open) does the viewer ask for one new link, once (a second "previewed" line); a second refusal shows "The file could not be opened…". AG-09 §3.8's "signed-URL with visible expiry" has nothing to show once the bytes are in memory: departure noted for the record, no expiry shown.
* **BR-8 Accept beside the preview** (r2, M3; AG-09 §3.8 line 483 "preview + the accept / needs-replacing controls live on one screen"): the panel's one primary button is **Accept this document**, CS-D1 part 2's `POST /checklist-lines/:id/accept` (no new API), shown only to holders of `agent/document:change-status` on a `received` or `being_checked` line; its 409 "Not ready for review yet." shows in the panel; on success the panel closes and focus goes to the line. Reject with a reason has no row (question 1) and is not in the panel. The row's "accept and reject stay where they are" is read through the requirement (AGENTS rule 2: the requirement leads; question 1 asks the founder to confirm).

## 4. Layout (EXPERIENCE §3 "Side panel", widened: the team's `Panel` with a wide variant; board S1-S3)
* **Width (r2, M4):** at 560 px the page gets about 512 px, so 9 pt print on an A4 scan draws at about 7.7 px (512 / 595 pt × 9): too small to read a balance or a name. The preview panel is `min(60vw, 960px)` from 1024 px up (about 860 px of page at 1440 px: 9 pt → about 13 px) and full width below 1024 px, a recorded departure from §3's 480-560 px (question 2). `Panel` gains one `wide` prop (one class), so every other panel is unchanged.
* **Entry (S1):** on a line with a clean current file, the file name becomes a link-styled button, label "Preview passport-scan.pdf"; a set with several current files gets one button per file. Only current files (the History dialog's earlier files: not built, §6b).
* **Panel:** header = file name (wraps), then the document type and the person, type and size ("PDF · 412 KB"), "Uploaded 21 Nov 2026 by Client A", pill "Checked: clean" (tooltip "Scanned for viruses before it could be opened"). Toolbar: Previous page · "Page 1 of 3" (live region) · Next page · zoom segmented control (Fit width default) · "Rotate" (tooltip "Turns the view only; the file is not changed"). Body: the page, one page drawn at a time; the page area is the only scroll area, at every zoom (m4). Footer: Close left, **Accept this document** right when BR-8 allows, else Close only. Focus returns to the file-name button on Close, to the line after Accept.
* **States (S2):** loading (a skeleton sheet, "Opening the file…") · still being checked, "Checking for viruses…" (Try again) · removed · contains scripts (a warn notice above the page) · image (no page controls) · no preview for this type (for later types; question 3) · could not open (sha mismatch or a PDF that fails to draw: "The file could not be opened. It may be damaged, or it changed since it was uploaded. Ask for it again.") · long names wrap · read-only by nature.
* **Phone (S3):** the panel takes the width; the toolbar wraps; no sideways page scroll. Keyboard: Tab through the toolbar; in the page area PageDown scrolls and turns to the next page only at the bottom (PageUp likewise), as Mozilla's viewer does (m4); Escape closes. 1024 px and 200 % zoom work.

## 4b. Best in class (vendor and project behaviour as remembered, not re-read for this concept: Unverified)
Mozilla's own PDF.js viewer: page number with total, previous/next, zoom presets including "Page Width", rotate, all keyboard-reachable. Google Drive and Box previews: a file opens over the list in place, name and size in the header, the list kept behind. Clio and Docketwise (immigration/legal case tools): document preview inside the matter, download as a separate action. **Copy:** the in-place panel and the PDF.js controls set. **Beat them:** the scan state said before anything opens, the "contains scripts" warning, a recorded opening, and no download needed to check a file. Effort saved: one click from the line, no file on the officer's computer to clean up later.

## 7. Questions (recommendation first)
1. **For the founder: Accept inside the preview?** (M3) AG-09 §3.8 puts Accept beside the preview ("open the in-app preview and click Accept"); the row says decisions stay on the line. **Recommend yes:** the panel's one button is Accept (CS-D1 part 2's route); Reject with a reason joins it once it has a row, which the tech lead adds beside Accept in CS-D1 part 2 (or a part 2b). Otherwise the officer closes the preview to accept every file.
2. **For the founder: a wider preview than the standard side panel?** (M4) **Recommend yes:** up to 60 % of the window (at most 960 px) from 1024 px, full width below, as a recorded exception to EXPERIENCE §3's 480-560 px; part 2's check measures a real Sample A4 scan at 1440 px (9 pt print at least 11 px). Between 1024 and about 1300 px Fit width stays under that bar (about 8.6 px at 1024), so there the officer uses 100%/200% with the page area scrolling; full width below 1024 px gives about 950 px of page at 1023 px.
3. **For the tech lead:** types beyond PDF, PNG and JPEG (**recommend** R1 previews those three only, the "No preview for this file type" state ready; conversion through `DocumentPdfPort.toPdf` is a later row), and where "contains scripts" is kept (brief, contract gap 2; part 1 recomputes until ruled).
