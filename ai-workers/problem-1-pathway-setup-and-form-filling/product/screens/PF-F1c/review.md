## The four gaps in the synthesized template
1. **Put not encrypted with aws:kms: closed.** Each of the three data bucket policies has `DenyPutNotKms` (`StringNotEquals s3:x-amz-server-side-encryption aws:kms`) and `DenyPutNoEncryption` (`Null … true`). Both apply to `Principal AWS:*`, `s3:PutObject`, `<bucket>/*`. The app's puts are not refused: `s3-files.ts` sends `ServerSideEncryption: "aws:kms"` with the key on every put, the tombstone put included (`send`, line ~102). No other code in `api/src` writes to S3. CopyObject is authorised as PutObject on the target and carries the header, so the copy command in RUNBOOK-restore step 5 is right. Check `bucketFindings`: exact-match, and six mutations caught (IfExists, AES256 allowed, narrower principal, bucket not objects, either statement gone).
2. **Access logs kept 90 days: closed.** There is a new `AccessLogsBucket` with: SSE-S3, BPA on, `BucketOwnerEnforced`, TLS deny, `ExpirationInDays 90`, abort after 1 day. Each data bucket has `LoggingConfiguration` with its own prefix. Delivery works through three `logging.s3.amazonaws.com` Allow statements, each with `aws:SourceArn` set to the data bucket and `aws:SourceAccount`. The CDK claims in the comments match aws-cdk-lib 2.275.0's own code: a KMS-managed target throws `KmsManagedKeyNotSupportedForAccessLogs`, and a customer key gets `grantEncryptDecrypt(logging.s3.amazonaws.com)`. `setContext` sits before any child, and the template shows the bucket-policy form. Checks: log bucket rules, logging target, and `logDelivery` exact-match. All can fail (tests lines 63–90, 141–162).
3. **Abort unfinished uploads after 1 day: closed** on all four buckets. The check is caught when the rule is removed, set to 7 days or disabled (×4).
4. **The task's FilesPort settings: closed.** The task sets `PLATFORM_FILES=s3`, the documents bucket `Ref`, the data key ARN (it matches `KMS_KEY` and the region rule in `choose.ts:48-49`) and `ca-central-1`. The link key is a new secret: 48 letters and digits generated by Secrets Manager. That satisfies `settings.ts:69` (32 or more characters, 10 or more distinct). The PR is right that the usual `{"placeholder":…,"random":…}` template would also pass the loader, so random is the correct choice.

## Least privilege and sufficiency for s3-files.ts
Synthesized grants: `s3:GetObject,s3:PutObject` on `<documents>/*/*`; `s3:ListBucket` on `<documents>`; `kms:GenerateDataKey,kms:Decrypt` on the data key with `kms:ViaService = s3.ca-central-1.amazonaws.com`. The data key policy has the account-root `kms:*` statement, so the IAM grant takes effect. They are sufficient:
* Put, conditional Put (If-None-Match / If-Match) and the tombstone each need PutObject plus GenerateDataKey.
* Get needs GetObject plus Decrypt. Head needs GetObject.
* ListObjectsV2 (`usedBytes`) needs ListBucket. With it, a missing key answers 404 `NoSuchKey`/`NotFound`, which the adapter maps to null. Without it, the answer would be 403 and become an error.
* Presigned GET is signed with the role's credentials and S3 calls KMS on its behalf, so ViaService holds.
* Every adapter key is `<uuid>/<FileKey>`, so it matches `*/*`.

There is no delete, and no other bucket is named. Unconfirmed (docs.aws.amazon.com not read here): conditional writes need no permission beyond PutObject, and with Bucket Keys a Put may also call Decrypt. Both are granted, so neither can break the app.

## Findings
**Major**
1. **The guard widening reaches every ECS task role and every way of attaching a policy. Only the service task role's `AWS::IAM::Policy` is held exactly.** `lib/checks.ts:398` adds S3 and KMS actions to `ECS_TASK_ACTIONS`, which `allowedFor` (`checks.ts:413`) applies to *any* task role. `filesTaskFindings` (`lib/service-checks.ts:378-390`) scans only `AWS::IAM::Policy` resources attached to the service's task role. Probe A gave the **migration task role** (`AppMigrateTaskRole…`) a new `AWS::IAM::Policy` with three grants: `s3:GetObject,s3:PutObject` on `<ExportsBucket>/*/*`, `s3:ListBucket` on documents, and `kms:Decrypt,kms:GenerateDataKey` on the data key **with no ViaService**. Result: `bypassFindings`, `filesTaskFindings`, `typeFindings` and `resourcePolicyFindings` all return `[]`. Probe B put the same grants as inline `Policies` on the service task role itself. Result: `bypassFindings` returns `[]` and so does `filesTaskFindings`. So the comment at `checks.ts:396-397` and the PR's "each held to its exact resource and condition by `filesTaskFindings`" are not true. Before this PR, any of these grants was refused. **Fix (small):** in `filesTaskFindings`, collect S3 and KMS statements from every policy form that reaches any task role (`AWS::IAM::Policy` with `Roles`, and the role's inline `Policies`; `ManagedPolicy` is already refused by `typeFindings`). Require none on a task role other than the service's, and exactly the three on the service's. Add probes A and B as fail cases. The alternative is to give S3 and KMS only to the service's task role inside `allowedFor`.

**Minor**
2. `lib/service-checks.ts:380-390`: the grant check compares JSON exactly, so action order matters. On the template the CLI deploys (`cdk.json` has `minimizePolicies`, which sorts actions to `["kms:Decrypt","kms:GenerateDataKey"]`), `filesTaskFindings` gives 2 false findings. `bucketFindings`, `bypassFindings`, `resourcePolicyFindings` and `backupFindings` all pass there. Sort `Action` before comparing. This is concrete evidence for the PR's question 3 (tests do not synthesize with `cdk.json`'s context).
3. `deploy/cdk/README.md:81` still says "a task role only `ECS_TASK_ACTIONS` (SES send)". Add the files grants, or point to `filesTaskFindings`.
4. `lib/service.ts:175` and the README "Buckets" line say "firm keys (`<firm id>/<key>`) and nothing else". `*/*` matches any key that contains a `/`, not only a firm-id prefix. That fits the row ("`*/` keys"), but the wording should say so. The firm-id shape is held by the adapter's `objectKey`, not by IAM.
