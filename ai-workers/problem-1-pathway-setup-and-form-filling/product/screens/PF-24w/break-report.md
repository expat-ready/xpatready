# PF-24w break report

## Break (supersede #2635) at 2f0a166ef

Scope: secrets and permissions (P-303). PLATFORM_ENVIRONMENT has no default; identityConfig and the Sample seed read PF-24's one loader; launchers set `local`. Isolated copy `brk15` on :4434 only (started, restarted 6 times, stopped). :4400 not used, live AI off, US$0. I ran loader probes from scratch scripts with tsx (no tracked file changed) and made real server starts with `tools/isolated.sh`.

### Findings

**M1 (Major). Demo › Reset answers 500 `ConfigRefused` ("The app cannot start") on a running server in `test`, and in `local` when a secret-box key is set.**
* Steps: (a) `isolated.sh brk15 4434 restart PLATFORM_ENVIRONMENT=test` with every required setting generated by the run. Then `POST /api/demo/reset {"confirm":"RESET"}` with `x-actor: user-A`. (b) The same in `local` with only `PLATFORM_SECRET_BOX_KEYS=2:…,1:…` and `PLATFORM_SECRET_BOX_KEY_VERSION=2` (plus `PLATFORM_IDENTITY=local`).
* Expected: the reset runs, and the Sample seed decision is made from the configuration loaded once at start (DW4: "read once per process").
* Actual: both answer **500**. api.log: `"errorName":"ConfigRefused"` at `settings.ts:147` via `configOf` in `sample-seed.ts:16`.
* Cause: `demo.ts:39` calls `sampleSeedDecision({ ...process.env, PLATFORM_SAMPLE_SEED: "on" })`. That is a copy, not `process.env`, so `configOf` calls `loadPlatformConfig` again. By then `platformConfig()` has deleted every secret from `process.env` (`SCRUBBED_FROM_ENV`, settings.ts:181). In test or production the copy is missing six required secrets. In local the copy keeps `PLATFORM_SECRET_BOX_KEY_VERSION` (not secret) but loses `PLATFORM_SECRET_BOX_KEYS`, so the key-ring rule refuses it.
* Before PF-24w, `sampleSeedDecision` used `identityConfig({...env, PLATFORM_IDENTITY:""})`, which needed no secrets, so this is a regression from this PR. Every reset path is hit: Reset (`demo.ts:552`, `wipe`), Reset to the six (it calls `wipe`), and the configured load (`demo.ts:449`).
* Probe output, same code in-process: local + secret box → `Missing required setting: PLATFORM_SECRET_BOX_KEYS`; test → `Missing required settings: PLATFORM_STRIPE_SECRET_KEY, … PLATFORM_SECRET_BOX_KEYS`; production → the same list (it should have been the quiet "refused: production never seeds").
* The same copy also breaks "read once": after a later `process.env.PLATFORM_ENVIRONMENT = "local"`, the demo path loads `local`, while `sampleSeedDecision()` with no argument still answers from the kept configuration.
* Why the tests miss it: `check_pf24w_environment` J-15 W1 sends ten requests and none of them is a demo route. The review's demo-reset suites ran in local with no secret-box key.
* The message no value leaks: it lists setting names only.

**m1 (Minor). The launchers silently replace a caller's *exported* PLATFORM_ENVIRONMENT with `local`, which then lets the stand-in in.**
* Steps: `PLATFORM_ENVIRONMENT=test PLATFORM_IDENTITY=local zsh tools/isolated.sh brk15 4434 restart`, with no `KEY=VALUE` arguments and no secrets. Then `POST /api/platform/session/local {}`.
* Expected: the caller's `test` is kept, so the start is refused (secrets missing, stand-in refused). Or at least it is not quietly turned into the most permissive value (rev 16.5 "fail closed").
* Actual: the copy starts (`isolated brk15 on http://localhost:4434`) as **local**. The stand-in's door answers **400** (open, input check), not 403 `LOCAL_SIGN_IN_OFF`.
* Cause: `isolated.sh:88` puts `env … PLATFORM_ENVIRONMENT=local …` ahead of `"$@"`, so only an argument wins and an exported value loses. `PLATFORM_SAMPLE_SEED` on the same line uses `${…:-on}`, so an exported value wins there. The two settings are handled inconsistently.
* `restart-api.sh:11` (prefix) and `start.sh:18` (unconditional `export`) force `local` the same way. A shell or CI job with `PLATFORM_ENVIRONMENT=production` exported that runs `start.sh` gets local, `PLATFORM_IDENTITY=local` and the Sample seed on, without a word.
* None of these can reach the cloud: the deploy goes through `container-entry.mjs`, which sets no default. Hence Minor. The comment "a setting the caller passes wins" is true for arguments only, and the review (line 79) says only isolated.sh lets the caller win, which also holds only for arguments.

### What held
* **Unset or blank values are refused:** unset, `""`, `"   "` and `"\t\n"` are refused at start. The real server exits before listening (port checked closed) and the log names PLATFORM_ENVIRONMENT and "local, test or production (there is no default)".
* **Odd spellings:** `Local`, `LOCAL`, `local,test`, a zero-width-space prefix and `sk_live_PASTED…` are refused as "not recognised". The value is never echoed, in the message or in the uncaught-exception print in api.log (grep: 0 hits). `production `, ` test`, `local\r` and a trailing NBSP are trimmed to valid values, which is acceptable.
* **The stand-in outside local:** `PLATFORM_IDENTITY=local` with `test` and every secret set is refused at the real start, naming the rule only. ` local ` is trimmed and refused the same way. `Local`/`LOCAL` are refused as invalid. A test copy without identity answers 403 `LOCAL_SIGN_IN_OFF`. Production with seed `on` gives "refused: … never seeds".
* **Odd values of the other settings:** `PLATFORM_SAMPLE_SEED=ON`/`sk_live_…`, `PLATFORM_POOL_MFA_REQUIRED=False` and a short `PLATFORM_LOCAL_SECRET` are refused by name, never repeating the value.
* **Secrets stay out of children and the log:** `PLATFORM_LOCAL_SECRET` is now a scrubbed secret. A child spawned after load does not see it, while `identityConfig()` still holds it. A test copy's api.log holds none of the 10 generated secret values, and neither does the local copy's log (secret-box keys: 0 hits).
* **Changes after load:** setting `process.env` after the load does not change `identityConfig()` or `sampleSeedDecision()` with no argument (M1 is the exception: the demo path).
* **Caller's value as an argument:** `PLATFORM_ENVIRONMENT=test` given to isolated.sh as an argument wins over its `local`.
* **start.sh's combination:** it cannot open anything outside local because it forces local (m1). `compose.test.yml` pins `local` with the stand-in, and the cloud entry sets no default.

Note, not a PF-24w finding (PF-24's scrub is in-process): the `tsx` wrapper process that is the server's parent keeps every secret in its own environment (`/proc/<pid>/environ`) for its lifetime.
