## Held (attempt, then the result)

* **One person on two cases, one visible and one hidden** (the same party on c1, where T has an open team row, and on c2, where T's row has ended), `search.search(tOwn, { email: "zoe@x.com" })`: named once (case c1) and `hidden_count: 1`. The door shows one hit.
* **Firm B searching firm A's exact values**: email `paul@x.com`, phone `+14165550177` and `416-555-0177`, names "Paul Tremblay" and "Tremblay": 0 matches, `hidden_count: 0`, no confirmers every time. `find(SOLO, { caseNumber: <A's number> })` gives nothing and 0. The door finds nothing. The prefix `C-2026` lists only B's own case. **No oracle across firms** by `hidden_count`.
* **view.own whose team row ended**: not named, counted (1). An upper-case staff id is lower-cased and still sees its own cases. A staff id that is not a uuid (ids only) is refused by a cast error; nothing leaks.
* **Case firm_id null, or different from its index rows' firm_id** (written past the triggers): neither named nor counted for firm A or firm B (the join `c.firm_id = i.firm_id` holds). An app path cannot produce it: `case_firm_from_key` refuses a mismatch, and the index needs the platform firm.
* **LIKE metacharacters** `%%`, `__`, `\\`, `''`, `%`, `Ana%`, `Ana%_`, `ana%_\'`, `O'Brien` through the port, and `%`, `C-2026-%`, `C_2026`, `\`, `'` as a case number: all are read literally. Only the person literally named "Ana%_\' O'Brien" matched. No injection: every value is a bound parameter.
* **Long text**: a 300-character name works, 301 is refused by zod. A 400-character stored name is cut to 300 for the port and 200 for the door title, and the door does not drop it. An empty title cannot occur (`case_party_index_name_check`, plus the "(no name)" fallback).
* **A phone with letters** (`416-555-O1O1`, `416555OIOI`, `1-416-JKL-0177`, `\u0000416`): `phoneOf` returns null and nothing matches; letters are never turned into digits. `+1 416 555 0177 ext 9` finds the right person.
* **A 1-character name or only spaces** (`"a"`, `"   "`): no name search (see m1 for the zero-width way round it).
* **The count across the 50-row cap**: 60 visible plus 7 hidden "Capper" rows gives 50 named and `hidden_count: 7`. With neither key: 0 named, 67 counted. The window count runs before `LIMIT`.
* **The audit line**: one line, with fields drawn from a fixed list (`name`/`email`/`phone`) and counts only. An extra key (`fields`) is refused by `PartySearchQuery`'s strict object, so neither the summary nor the detail can carry a searched value. When the audit write fails the search answers nothing (the PR's DW11; the line and the answer are in one transaction).
* **An answer written in a rolled-back transaction** (family name plus email, with `SET CONSTRAINTS ALL IMMEDIATE`, then `ROLLBACK`): the index row is unchanged, and `rolled@x.com` finds nothing.
* **The finder without `agent/case:show`**: no groups. With show but no view key: no groups.
* **Wrong-shape hits**: a long title is cut to 200 and the subtitle stays under 300. A case-number hit is never zod-parsed, so only the 9-digit party row in m2 breaks the search.
* Hidden employer rows (one per stage) count once per row, the same way the port names visible ones (DW10). This is consistent, so not a finding.
* **Observation, not a finding:** within one firm a view.own person can probe hidden people through `hidden_count` with any 2-letter prefix or fuzzy text ("Tr" → 1, "Trx" → 1 by similarity 0.5, "Pb" → 0). This is the contract's "counted" rule widened by prefix matching (the fake counts exact name keys only). Each port search writes an audit line.
