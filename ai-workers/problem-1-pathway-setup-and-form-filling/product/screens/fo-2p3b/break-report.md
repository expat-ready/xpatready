## Findings

**M1 (Major): a PHONE booking by a person with an open prospect throws away the phone number the booker typed.**
Steps: person P has no phone on file and one open prospect at Engaged. On the public page P books with mode PHONE and phone `+1 416 555 0123` (the page refuses PHONE without a number, `service.ts:278`). Result: 201. The receipt is ON_OPEN_PROSPECT and the prospect moves to Consult, but `contactOf(P)` returns no phone, and the number is in no row: not `fo_person`, `fo_booking` or `fo_note` (probe H1). The same happens when the number on file is old and the booker types a new one.
Why it is wrong: the visitor had to type the number to book a phone call, and the host now has no number to call, or the wrong one, with no sign of it. The new-person path keeps the phone (`arrival-port.ts:60`). The open-prospect branch (`arrival.ts:67-75`) uses only the person id, so everything the booker typed except the email is dropped. AG-2-10 rule 3 lists "name, email, phone" as what a booking carries. Either keep the phone (on the person when the record has none, or as a note), or refuse to treat a PHONE booking as on-file without a number.

**m1 (Minor): lock-order deadlock between a booking and a web-form or hand-added arrival with the same email and phone.**
`bookingArrived` takes the email lock first (`arrival-port.ts:44`). `arrive()` then takes the locks for [email, phone] in sorted order (`arrival.ts:82`), and "+…" sorts before letters, so a booking holds the email lock and waits for the phone lock. Any other door takes the phone lock first, then the email lock. Steps (repeatable with a third session holding the email lock and then releasing it): the booking and a MANUAL `arrive()` with the same email and phone start together. Result: the hand-added lead fails with `40P01 deadlock detected`; the booking succeeded (probe L1). The web form and Add lead have no retry (`busy.ts` is not on that path), so the visitor or staff member gets a 500. The booking side retries only because `isContention` covers 40P01. Take the lock after the phone too, in the same sorted order, or do not take it before `arrive()`.

**m2 (Minor): race: a prospect closed while a booking is running leaves the booker with no lead and no open prospect.**
`holders` (`arrival-port.ts:46`) is read without a row lock. `moveToConsult` reads it again later `for update` (`:118`). Steps: session S marks the prospect LOST and has not committed yet. The booking reads it as open, takes the ON_OPEN_PROSPECT branch, then waits on S's row lock. S commits. Result: receipt ON_OPEN_PROSPECT, no lead, prospect LOST, so the booking lands nowhere in the pipeline (probe Z1). It should become a new lead, as R6 below does when nothing is racing. Lock the holder's prospects before choosing the branch.

**m3 (Minor, needs a ruling): one email shared by two people who each have an open prospect makes a third person and a new lead.**
Steps: two people of firm A with one email (allowed: shared family email, AG-2-84 §12), each with an Engaged prospect. That email books. Result: a new person and a new OPEN lead, flagged against the newer of the two only. Neither prospect moves (probe T1). AG-2-10 rule 2 says "booker on file and the subject or main contact of an open prospect → no lead"; the code requires exactly one holder (`:61`). "Duplicate beats a miss" (AG16-60) may be the intended reading, but neither the brief nor the port header says so. The founder or Lead B should decide.

**m4 (Minor): the adapter accepts a stale wording version of the firm.** In process, `bookingArrived` with firm A's older wording v1 (v2 is current) records a consent on v1 (probe C7). `:53` checks firm, channel and purpose, but not that the wording is the current one. The public door is safe because `service.ts:285` returns 409 first (C4 held), but the port header gives the adapter "the firm's wording" as its own rule.

**m5 (Minor): a repeat of an ON_OPEN_PROSPECT key can return different ids.** Booking id X arrives and returns `{personId, prospectId: P}`. P is then marked lost. A repeat of X returns `{personId}` with no prospect (probe I4), because `repeat()` works the prospect out again (`:38`, `onlyOpen`) and does not read what the first call returned. The brief says "a repeat returns the same ids". There is no live trigger today: booking ids are random for each attempt.

**m6 (Minor): `bookingForPerson` is not idempotent by booking id.** The port header (`ports/arrival.ts`) says "Idempotent by `booking:<bookingId>`". Steps: call it for booking X, a person moves the card back to Qualified, then call it again for X. Result: a second BOOKING move (probe F4). Forward-only is the adapter's only guard (`:71-79`).

**m7 (Minor): `bookingForPerson` and `contactOf` throw for a 36-dash id instead of returning null.** The id check `/^[0-9a-f-]{36}$/i` (`:74`, `:90`) lets `"-".repeat(36)` through, and Prisma then throws "Invalid uuid" (probe F2/F3). Other non-uuids return null as they should. HTTP cannot reach this (`StaffBookingBody.personId` is `z.uuid()`). A full uuid pattern, like `ports/arrival.ts`'s `Uuid`, would close it.

## What held
* **Consent.** No tick → zero `msg_consent` rows, and the person and lead are still made. Tick → exactly one row: the firm's current wording, BOOKING_FORM, EMAIL/MARKETING, locale en-CA. On the public door, a stale v1, firm B's, an unknown or an SMS wording id → 409 with nothing written. An upper-case wording id is stored lower case. `consent:false` with an id → no row. A string `"true"` → 400. In process, firm B's or an unknown wording throws and the arrival rolls back. On an open-prospect booker the tick → one row on the existing person, and a later no-tick booking adds or withdraws nothing.
* **Idempotency.** The same booking id twice at once → one person, one lead, one receipt, the same ids. The same with an open prospect → one receipt and one move. An upper-case repeat id with other details → the first person, nothing new.
* **Concurrency.** Two simultaneous public bookings by one new email → two people and two leads, the later flagged against the earlier (AG-2-84 §12). Three simultaneous bookings (email in upper case) by an open-prospect holder → no lead, exactly one move, and all three bookings name the person and the prospect.
* **Prospect rules.** Engaged → Consult once with cause BOOKING, one audit line ("Consult booked: P-… moved from ENGAGED to CONSULT"), one `prospect.stage_moved` event, and the move chained from the right stage. At Consult → no move row. Past Consult → never moved back. Two open → none moves and no prospect is named. NURTURE, LOST or WON only → not open, so a new lead. NURTURE + LOST + one Engaged → the Engaged one moves. Consult turned off → no move and no error. A booking's move adds a stage-move row, so a staff board holding the old version gets the stale-version 409.
* **Corporate.** The primary contact books → no lead, and the Corporate prospect moves to Corporate Consult. A non-primary (HR) contact → a new lead. A person with one Individual and one Corporate open prospect → none moves.
* **Firm separation.** A firm B booker with the email of a firm A prospect → a new person and lead in B, A untouched, no cross-firm flag. `bookingForPerson` and `contactOf` with A's person under B, an unknown uuid, "not-a-uuid" or SQL-like text → null. An upper-case own id works. Firm B with A's wording → refused.
* **No front office.** Two simultaneous first bookings of firm C → both 201, seeded once (16 stages). On :4564 the real app seeded `sample-firm` at its first booking: lead L-00001, door BOOKING, source "Booking page", receipt CREATED `booking:<id>`, zero consent rows, audit "Lead L-00001 arrived by a booking." A DELETED firm or an unknown firm id → the arrival fails whole.
* **Personal data.** No email, name or phone appears in any `audit_event` summary or detail, or in any `module_event` payload (81 lines, 55 events). Actors are typed. The receipt's `payload_hash` is an unsalted sha256 of the person JSON, as the web form and Add lead already do; it is not new here.
* **Database checks.** Every BOOKING receipt is completed (CREATED with a lead, or ON_OPEN_PROSPECT with none). Every booking lead has its receipt, every booking names a person and has its own receipt with the same person, and there is one receipt per key.
* **Text.** A 100-character accented name and a Persian name with a ZWNJ are stored as typed. 101 characters → 400. Mixed-case email → stored lower case. Extra body keys (`personId`) → 400.
