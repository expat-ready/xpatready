## What held

* **No line on a firm the breach does not name.** Breach {A,B} read with `?firm=C&firms=C&affectedFirms=C` and headers `x-firm-id`, `x-firm`, `x-tenant-id` set to C: lines on A and B only. The platform line's detail has no `firm` key, because `:id` does not declare `firmFilter`. A GET with a JSON body `{affectedFirms:[A], firmId:A}` plus `?firm=A` on breach {C} got 400 and wrote nothing. The breach id in upper case got 200 with the same two lowercase firms. Firm ids come only from the database row (service.ts:226), never from the request.
* **Refused reads write nothing.** Each of these wrote 0 `audit_event` rows for its correlation id: a firm token (403 FIRM_SESSION_REFUSED), our Support and Admin (403 MISSING_PERMISSION), no token (401), an unknown uuid (404), a malformed id (404), and HEAD as Support (403). None of them leaked body fields.
* **Roles.** The Owner and the Auditor get 200, each line under that reader's own `ourstaff:<id>` / OUR_STAFF word (checked in parallel: owner and auditor lines never swapped). A breach naming no firm writes only `cross_tenant.access`.
* **Notes outside the read route.** `PATCH /register/breaches/:id` (@NoFirmData) writes 0 lines. `POST …/notices` (@ChangesFirm) writes only `platform.breach.notice_sent`. `one()` has one caller, routes.ts:25. The tracker is read only in the reads-across branch.
* **All or none.** A trigger refused only firm B's (the 2nd) firm-read insert: 500 `Internal server error`, no breach data, no `cross_tenant.access`, no line on A, exactly one `audit_write_failed` alert naming B. Refusing only the 200th firm gave the same: 0 firm lines, 1 alert. The only row left is the firm-names lookup's `platform.bypass` line, written earlier in its own transaction (as on main).
* **200 firms: correctness.** Exactly 200 `platform.system.firm_read` lines, one per named firm, plus 1 `cross_tenant.access`. 0 lines on a firm outside the 200. Repeated reads give 202 every time. A one-firm read beside 20 big reads answered in 160 ms with the right lines.
* **Concurrency.** 80 reads, 8 at a time, mixing breach {A,B} and breach {C} and owner and auditor tokens: 0 mismatches against the expected lines per correlation id.
* **Duplicates and mixed case.** `affectedFirms: [A, A in upper case]` is refused 422 "Name each firm once." on open and on change (Uuid lowercases before the Set check). The tracker's Set lowercases and de-duplicates the affected and notified firms.
* **Firm views.** The line appears in firm A's Activity log (ours=1, "ExpatReady staff read the firm's records") and in our access report for A. Firm B's report does not contain the read of a breach naming only A and C.
* Known limit, not new: a client-sent `X-Request-Id` is reused as the correlation id. Firm C's line can therefore share one with an earlier read of {A,B}, as lines.ts:23-25 already states.
* HEAD on `:id` runs the handler and writes the same lines with no body. That is accurate (the server read it), noted only.
