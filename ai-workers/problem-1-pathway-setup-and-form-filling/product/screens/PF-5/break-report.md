# PF-5 part 1 — break report

Breaker (runtime, money, public door, schema), 15 Nov 2026. Commit `1cd85d6c` on `claude/upbeat-ptolemy-wfwnl1` (PR #1815). Isolated copy `brk5` on :4571 (`PLATFORM_IDENTITY=local`, fake billing, no Stripe network), database `xr_studio_brk5`; stopped after. Over HTTP: curl. For verify: a service-level script built like `tests/check_pf5_signup_billing.ts` (FakeClock, LocalSignUp, fakeMail, real `auditEvent`), run against `xr_studio_brk5` with the per-IP limits raised, so many cases could run. SQL by psql. File paths are under `prototype/studio/`.

## Findings

**M1 — Major. Timing shows whether an email is known.** Steps: 40 `signUp` calls on each path, each with a valid stamp, timed in the service. Median: new email 10.6 ms (p10 9.8, p90 13.0); known account 3.0 ms (2.6 / 3.7); live pending 6.3 ms; honeypot 1.7 ms. The ranges do not overlap. The body and status are the same each time, but a known email answers about 3x faster: it does one mail send, while a new email does the advisory-lock transaction plus `identity.register`. The gap will grow with part 2's Cognito `SignUp` (a network call) on the new-email path only. Expected (row PF-5: "the same answer whether or not the email is known"): the same work and the same latency on every path, for example by sending the mail or doing the registration after the reply, or by padding to a fixed time. `api/src/platform/firms/signup.ts:110-128`.

**M2 — Major. Anyone can hold an email's sign-up for 24 hours with their own password and firm name.** Steps: (1) an attacker signs up `victim@…` with password `attacker-chosen-pass-1` and firm "Attacker Firm"; (2) the victim then signs up with their own password and firm. Result: 202 both times. The victim's inbox holds only the attacker's verification email. The pending row still says `firmName: "Attacker Firm"`. If the victim opens that link (it is the only one they get), they confirm a firm and an identity whose password the attacker chose. If they do not, they cannot sign up for 24 hours, and their own attempt sends nothing. This also hits an honest person who mistyped their password: they cannot start again for a day. Expected: a new sign-up for an email with a live pending row replaces it (a new token, the old row ended) or at least resends. Proof of the password should rest with the person who confirms, for example by asking for the password at verify or after it, not when the row is created. `signup.ts:119-120` ("if (live) return;"); the migration's update rule (`migration.sql:116-119`) allows no change except `used_at`, so the pending table cannot even mark the old row ended.

**M3 — Major. A genuine sign-up is silently lost after a restart, on a second instance, or when the form was open over 2 hours.** Steps: a stamp signed by another `FirmSignUp` instance (another process key), 10 s old, then a normal body. Result: 202 "we have sent a message", with 0 pending rows and 0 emails. A form submitted 2 h 1 s after it loaded gives the same result. `formKey` is `randomBytes(32)` per process (`signup.ts:65`). So every deploy or restart, and every request that lands on an instance other than the one that served `GET /plans`, is treated like a bot: the person is told to check their email, and no email ever comes. Expected: the key is shared by every instance and survives a restart (config or secret store). A stale or foreign stamp from a real browser gets a visible "reload and send again" (400), not the bot's silent 202. Only the honeypot should stay silent. `signup.ts:65,109,196-201`.

**m1 — Minor. Field errors lose their field name.** `POST /api/public/signup` with `{}` returns `errors: ["Invalid input: expected string, received undefined" ×3, "countryCode: CA only for now"]`. With `{email:5, firmName:null, period:"WEEKLY"}` there is still no field name. The rule "keep the message if it has a ':'" (`signup.ts:98`) matches zod's own messages ("Invalid input: …"), so the path is never added. PF-5s's form cannot place these errors on the right field. Expected: `email: …`, `firmName: …`.

**m2 — Minor. The per-IP limit is unusable behind a proxy and weak on IPv6.** `X-Forwarded-For: 10.0.0.N` did not get around it (held: the 10th request was 429). But no `trust proxy` is set anywhere in `api/src`, and `ipOf` uses `req.ip` (`routes.ts:259`). Behind a load balancer every person has the balancer's address, so 10 sign-ups per 10 min is the limit for everyone, and anyone can use it up. The key is the full address, so one IPv6 /64 gives unlimited keys. The map lives in memory per process (`signup.ts:62,186-192`), so N instances give N× the limit. Expected: trust the known proxy hop, key IPv6 by /64, and keep the counts in a shared store.

**m3 — Minor. A known email's owner can be flooded.** Every sign-up for a known email sends "You already have an account" again (`signup.ts:111-112`). There is no per-email cap, only the per-IP one (see m2). Expected: at most one such email per address per window.

**m4 — Minor. When mail fails, the status shows the email is known.** With `mail.send` throwing: known email → 500 (the error escapes), new email → 202. `signup.ts:112`. Expected: a mail failure on the known path still answers 202 (log it or queue it).

**m5 — Minor. Wrong codes have no per-token cap.** 2000 wrong 6-digit codes on one token (limits raised): 2000 × `CODE_WRONG`, no lock. The correct code worked after that. Over HTTP only the per-IP 30 per 10 min applies (`signup.ts:132,138`; `signup-identity.ts:37-41`). The impact is low today: the 256-bit token and the code arrive in the same email. Expected: about 5 tries per token, then the token is ended.

**m6 — Minor. The pending table's rules have gaps (direct SQL; the app does not do these).** (a) `INSERT … terms_version_ids = NULL` is accepted: the column is nullable, `cardinality(NULL)` passes the CHECK, and the trigger's `count <> NULL` is not true. Verify would then make a firm with no terms acceptances (`migration.sql:57,96,122`). (b) `created_at = now()+100 years, expires_at = created_at+1 h` is accepted. The "24 h" ceiling is measured against a client-supplied `created_at`, so the row cannot be deleted for 100 years and that email is blocked (`migration.sql:95,113`). (c) `used_at` may be set to any time, for example 5 years ahead (`migration.sql:117`). (d) `TRUNCATE platform_signup_pending` succeeds: it has no truncate trigger, unlike the terms tables (`migration.sql:127`). Expected: `NOT NULL`, `created_at` checked against `now()`, `used_at` close to `now()`, and a truncate rule (or a written note that truncate is allowed).

**m7 — Minor. A plan switched off between sign-up and verify still gets a trial.** I signed up on `solo`, set `active=false`, then verified: a firm and a TRIAL subscription on the inactive plan (`signup.ts:140`, `findFirstOrThrow({code})` does not check `active`). Expected: refuse with a plain message, or record that this is the intended rule.

**m8 — Minor. A password of 12 spaces is accepted.** It is stored as a pending row and passed to the identity provider (`signup.ts:48`). Cognito would refuse it at `register`, which would surface as a 500 inside the transaction. Expected: the same rule as the provider's policy, refused with a field error.

**m9 — Minor (part 2 interface). Registration and its email happen inside the DB transaction, before the insert.** `identity.register` sends the verification email before `platformSignupPending.create` (`signup.ts:122-126`). If the insert or commit fails, the person has a link that answers 404. With Cognito, an unconfirmed user also stays behind: a sign-up again after the 24 h expiry calls `SignUp` again for the same email and gets `UsernameExistsException`. The `SignUpIdentity` interface has no resend or replace (`signup-identity.ts:12-18`). The local stand-in hides this.

## What held
- XFF spoofing does not get around the per-IP limit (429 on the 10th request). `[]`, `null` and `"str"` bodies → 400. Unknown keys and `__proto__` are refused or ignored. Strict object.
- Five concurrent sign-ups for one email in mixed case → 1 pending row and 1 email (advisory lock plus the lower-case CHECK). `emailOf` refuses full-width and decomposed forms.
- Five concurrent verifies with the right code → 1 firm and four 404s. A third verify → 404. A malformed token or code → 404.
- Terms: one missing or one extra id → 400. Duplicated or upper-case ids collapse to the current three (acceptable). A 50,000-item array is handled. A terms version dated in the future is not offered.
- Password is never written: absent from `platform_signup_pending`, `audit_event`, `module_event` and the API log (request lines carry no body).
- firmName: bidi (U+202E) and control characters are refused. A Chinese name gives key `firm-8d2239f9` and verifies.
- Terms tables: UPDATE and TRUNCATE are refused. A pending row's DELETE before expiry is refused. A second change after `used_at` is refused.
- Honeypot and too-fast form → 202, nothing stored or sent. One `firm.created` event per firm, last in the transaction. A firm with no Stripe price → `checkoutUrl: null` plus "Sign in to finish…", and the firm stays PROVISIONING.
