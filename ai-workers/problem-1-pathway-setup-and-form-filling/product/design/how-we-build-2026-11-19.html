1 · The road a change takes

Lead (Mac) Cloud builder GitHub machines Your Mac AWS Canada (planned)
  1. 1 · Lead · shape

    A backlog row is made ready

    One small piece of a Release 1 item, with what "done" means, your decisions quoted, and the files it may touch, so two builders never edit the same file.

  2. 2 · Cloud builder · build

    A builder writes the code on its own branch

    One fresh cloud session per row. It builds on a copy, runs the tests, and opens a pull request (PR). This is the "dev" stage: every builder has its own private copy of the app.

  3. 3 · GitHub · CI

    Automatic checks run on every PR

    Tests split across many machines, plus guards (no secrets, no team-app detail, size limits). Red means it cannot merge.

  4. 4 · Independent reviewer

    A fresh AI reviewer approves

    A separate Opus session that did not write the code reads it against the row. For money, permissions or deletion, a "breaker" also tries to break it. Then it gets the label review: approved. The Lead reads anything touching money, permissions or the database itself.

  5. 5 · GitHub · merge queue

    Mergify merges approved PRs in batches

    It tests each batch together against the newest main, then merges it. Records (documents) have their own lane. Coming next (P-715): one lane per module, so a failure in one module stops blocking the others.

  6. 6 · Your Mac · demo

    The demo at localhost:4400 updates itself

    After every merge, a job on your Mac moves the demo to the new main and keeps its data. Today it shows main as of 04:13 IST. working

  7. 7 · qa · prove

    qa tests it like a person and counts it Proven

    qa walks the merged screens and checks the data underneath. Only then does a Release 1 item count. Every night a full run of all tests checks nothing old broke.

  8. 8 · AWS Canada · CD to staging

    Deploy to a staging server not built yet

    PF-8a: the AWS setup written as code. PF-8b: the app running on AWS with its secrets and mail. PF-8c: deploy from GitHub by a button or tag, with a way back to the last good version. Your choice today: get them ready now, start when Proven reaches 30.

  9. 9 · Later · production

    The same deploy, to the live environment

    Same code path as staging. Real firms, real users and the real domain come with it.

3 · Why staging was not raised with you before

That was our miss. The staging rows (PF-8a, 8b, 8c) have been in the backlog since about 15 Nov, and P-625 (16 Nov) settled its web address. But they were ranked behind capability rows, because the plan says critical features first (P-576). No Lead put them to you as "this is where you will test". The Mac demo became the default test place without anyone asking whether that was enough.

4 · What a staging server gives us

  • Testing from anywhere: you, the immigration expert or a pilot firm open a web address. Your Mac does not need to be on.
  • Real conditions: real email, file storage, sign-in and backups in Canada. The Mac demo fakes these.
  • Less load on the Mac: qa can prove items on staging. Today the Mac is short of disk (6.9 GB free).
  • A safe rehearsal for launch: the same deploy and roll-back that production will use, proven early. R1.14 (backups) needs it anyway.

5 · The demo at :4400: keep it, or replace it?

It is not a separate old POC. Release 1 is being built inside the same app, so what you see there is Release 1 so far. Its first screen is still the configurator from the POC, and it still says "Prototype · demo workspace". New Release 1 parts (cases, money, client portal) are added behind it as they merge.

Your safety copy: git keeps every version. Any earlier day's app can be brought back in minutes. We can also pin today's version under a fixed name, so "the version that worked" is always one step away.
