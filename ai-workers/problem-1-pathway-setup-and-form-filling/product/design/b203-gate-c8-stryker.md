## Technology gate record: c8 (per-suite coverage) and Stryker (mutation testing) for B203 (STANDARDS §1, P-744) — open: waiting for the reviewer's Approve and the tech lead's read; nothing installed
Asked for by P-744 (founder, 20 Nov 00:2x IST, "Yes, start now"); read on npm and the projects' repositories 19 Nov ~19:30 UTC (20 Nov ~01:00 IST). Install happens only in the PR that first uses each tool, after this record is approved.
* **Problem.** Nothing maps a test to the code it runs or to the capability it proves: suite selection reads usage lines and imports (`select-suites.mjs`), so a PR pays ~7.3 job-hours when a full run is asked (P-733), and a green suite says nothing about whether its assertions would catch a wrong line (P-742, P-744). Two measured gaps: (1) test → file → module → capability, generated, for test impact analysis and a traceability matrix; (2) how strong the tests are (mutation score), not only how much they run (line coverage).
* **c8 — no new tool.** Already in the stack: `prototype/studio/package.json` devDependency `c8` **12.0.0** (exact pin, lockfile integrity), used with qa's harness `tests/qa/coverage-preload.mjs` (P-69; the preload only lets a server started with `NODE_V8_COVERAGE` write its coverage when stopped; c8 reports it). Version 12.0.0 published 14 Jul 2026 (over four months old); licence ISC; source github.com/bcoe/c8 (npm `c8`); `engines.node` `^20.19.0 || ^22.12.0 || >=23`, so Node 24.21.0 fits; npm integrity `sha512-4zpJvrd1nKWutnnKC2pXkFmb6iM1l+ffN//o1CzlTNwW7GSOs9a1xrLqkC48nU8oEkjmPZLPiwMsIaOvoF4Pqg==`. B203 adds a use, not a dependency: each suite runs with `NODE_V8_COVERAGE` (V8's own coverage, so `tsx` code needs no instrumenting step) and its server child writes coverage on stop through the existing preload. The map is per suite, not per test case (a suite is one script; its checks share one process). Known costs (`lanes/qa.md`, "Earlier lessons (28 Oct)", step 4): coverage needs a quiet machine (timing steps go red above a load average of about 10) and `check_p2_guard` always fails under the preload. Also (this lane's reading, not from qa.md): suites that share one server cannot be told apart by that server's coverage; so the map runs suite by suite on its own GitHub runner, and a suite that cannot run under coverage is listed as unmapped (it then always runs, never skipped). Option weighed: nyc/Istanbul 18.0.0 (ISC): rejected, it instruments source and needs a transform for `tsx`; c8 is already here.
* **Stryker — new, in a pilot only.** `@stryker-mutator/core` **10.1.1** (published 23 Oct 2026, 27 days old on 19 Nov), licence Apache-2.0, source github.com/stryker-mutator/stryker-js (npm `@stryker-mutator/core`), `engines.node >=22.0.0`; npm integrity `sha512-4xJAOCw9utJMLyrTk9gINi434tBxnyuwt8lU/InyoKagKd2/zh/2ui7ncWoD0qZeJrxClYzblg8iUh5ewBAB3Q==`; unpacked 1.2 MB plus its dependencies (rxjs, execa, ajv, commander and others, all pinned by the lockfile). Optional, same release: `@stryker-mutator/typescript-checker` **10.1.1** (Apache-2.0, peer `typescript >=3.6`; we pin 6.0.3), integrity `sha512-Tgsqu+bYPS10jzvRHKXdLTuGEyma1sjJ8lKqqtU+sylqbpYznz41YiBflQaE61UEeutXAIbENrb06GkImWOJ0A==`, which drops mutants that do not type-check before any test runs (fewer runs).
* **Runner (correction to the brief).** There is no "tsx runner" for Stryker. Its runners target Jest, Vitest, Mocha, Jasmine, Karma, Cucumber and TAP; our suites are plain `tsx` scripts that exit non-zero on a failed check. So the pilot uses core's built-in **command runner** (no extra package): `testRunner: "command"`, `commandRunner.command` = the pilot module's own no-server suites. Its cost: the command runner gives Stryker no per-test coverage, so every mutant re-runs the whole command (`coverageAnalysis` off). That is why the pilot is one module with fast suites, run in a dispatched job, never on a PR. Middle option weighed: `@stryker-mutator/tap-runner` 10.1.1 (same release and licence) runs each file with `node` and its `tap.nodeArgs` (here `--import tsx`) and records coverage per test file, so each mutant runs only the suites that reach it; its cost is that the pilot's suites must print TAP lines, and it is a second package through this gate. If the command runner's run time breaks the reconsider line below, the TAP runner is the next step before any move to Vitest. Converting suites to a supported runner (Vitest is in STANDARDS §1's default stack) is a later decision, not part of B203.
* **Pilot target (flag now, chosen in PR 5).** Stryker mutates JavaScript and TypeScript only. Much of the money ledger's rules live in SQL triggers and views (`prototype/studio/api/src/client-money/MODULE.md`: "No code here yet", tables and rules in migrations), so mutating the ledger's TypeScript would test little of it. The firm walls have TypeScript (`api/src/platform/firm-scope.ts`, 254 lines), but their suite `tests/check_pf12_walls.ts` starts the API and builds three scratch databases, so it is too slow to re-run per mutant. PR 5 picks the module whose TypeScript logic has suites that start no server (or adds such a suite first) and says why.
* **Options weighed.** No mutation testing: keeps the gap. mutode 1.4.2: released 3 Jun 2018 (npm's May 2022 date is a metadata change), unmaintained, rejected. Hand-written fault seeding (`check-guards.sh --mutate` already does it for the guards): fine for a few guards, does not scale to app code. Stryker is the maintained standard for JavaScript and TypeScript.
* **Integration and upkeep.** devDependencies in `prototype/studio/package.json`, exact versions, lockfile integrity (as today); one config file next to the pilot; one `workflow_dispatch` or scheduled job; never on a PR or in the merge batch, so no bar changes and no PR waits on it. Upgrade only through this gate. Licence impact: c8 is ISC and Stryker Apache-2.0, both permissive; they are dev tools, never shipped in the app, so no licence duty reaches the product (Unconfirmed: no counsel). Data: runs on our code and sample data only, no network at run time, no personal data. Cost: US$0 (open source; the CI minutes are free on this public repository).
* **When to reconsider.** If the pilot's mutation run takes over 60 minutes for one module, or its score cannot be acted on (survivors that are not real gaps above about a third), stop at the pilot and record why; if suites move to Vitest, switch to `@stryker-mutator/vitest-runner` for per-test coverage.
