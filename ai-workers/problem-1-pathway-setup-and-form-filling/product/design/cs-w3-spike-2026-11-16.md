## The answer to contract §8 (step 5's figure)

**One cause, not five.** With `ENABLE` + `FORCE ROW LEVEL SECURITY` on the case-side tables and the API on PF-12's app role (`xr_app`, owns no table, no `BYPASSRLS`), every failure comes from one cause. **A case-side request carries no firm.** The staff (`x-actor`), the simulated client and link sessions all hit it, and so does the first write of an opening (the new `party` row is refused). Reads come back empty and turn into "No such case." (404); writes fail with 500.

Once the firm is set for case-side requests, the case-side suites tried all pass, in each area:
* interactive `$transaction`s;
* raw SQL;
* CS-W1's `SECURITY INVOKER` fill triggers, which read the parent case under the wall;
* the case-number counter;
* the checkpoint loader and the demo reset.

The firm is set here by a per-database stand-in for part 1's middleware: mode B, below.

The reason is in PF-12's wrapper (`api/src/platform/firm-scope.ts`, `WalledPool`). It sets `app.firm_id` and the role on the pooled connection at **every checkout**, from the caller's async scope. A transaction holds one connection, so it keeps that firm. So PF-12's wrapper already covers interactive transactions and raw SQL centrally, and the `Db` class is already that walled client (`core.ts:36`).

* **Step 5's re-size:**
  * contract today: 2 / 5 / 12 small changes;
  * measured: **1 / 2 / 4**. Part 1, the doors and the request context, is the change. Part 3, background and loaders run as the Sample firm, is the second. Part 2's 100 per-site fix-ups are **not needed**: no suite failed on a transaction or raw query once a firm was set.
  * The high figure keeps room for the untested items listed under "Not measured".
* **Part 2 shrinks to a census check.** Part 1's census (`tests/check_csw3_firm_scope.ts`) can start from the allow-list below. Each area's journey then only has to pass with the firm set, which mode B shows it does. Part 2's per-area PRs become "the journey passes with the walls on; the area's files leave the list", with no code change expected. The exception is the configuration files that read case tables across a workspace: they count cases, and under the walls they count only the caller's firm's (`studio.ts`, `where-used.ts`). Whether that is right is a product question, below.

## What the spike decides

* **Part 1 is the work.** One middleware for `/api/runtime/*`, `/api/link/*` and `/api/demo/*` puts the firm into PF-12's scope (`setRequestFirm` after PF-4's `enterRequest`, the same seam as `guard.ts:100-109`):
  * staff by `x-actor`: CS-W1's `firmIdByKey`;
  * the simulated client: the case's firm;
  * link sessions: the session's firm.

  A second `AsyncLocalStorage` or a `Db` factory is **not** needed: `Db` is already PF-12's walled client, so the draft's "Db subclass" point is settled by PF-12. The two narrow lookups (`case_firm_of_link_session`, `case_firm_of_case`) stay as the draft says.
* **Part 2 needs no per-site code**, on this evidence. It keeps its census lines and its journey-with-walls check per area.
* **Part 3:** the loaders pass with the firm set as the Sample firm (C10.1 48/48, Reset to the six 25/25), so the demo routes need only that firm in their scope. `health.ts`'s and the background runs' firm stays to name.
* **CS-W2 is unblocked:** the default-plus-trigger fill works under the walls (filing via `case_firm_fill`, party via its default).
