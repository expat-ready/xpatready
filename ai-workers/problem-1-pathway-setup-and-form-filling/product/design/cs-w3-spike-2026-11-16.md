## The answer to contract §8 (step 5's figure)

**Three causes**, two measured and one found by reading the code. Contract §8 asks for the count of distinct causes, not of failing tests.

1. **A case-side request carries no firm** (measured, mode a).
   * Who hits it: the staff (`x-actor`), the simulated client and link sessions.
   * What happens: reads come back empty and become "No such case." (404). The first write of an opening is refused (`party`) and answers 500.
   * The fix: part 1, one door that puts the firm in PF-12's scope.
2. **A firm-scoped bulk write silently skips the other firm's rows** (measured, both modes).
   * With one case of each Sample firm present, `POST /demo/reset` answers 500 and **every case survives**.
   * How: `demo.ts`'s `case.deleteMany` deletes only the rows the wall shows, with no error. In mode a it deletes none; in mode b only sample-firm's. The leftover case's `pack_work_pin` then blocks the `config_release` delete (`RESTRICT`).
   * The fix: part 3. The reset runs once per Sample firm, or on a named bypass use. It cannot run as one firm. A row-level-security error count cannot see this cause, which is why the reset is probed directly.
3. **Background and start-up work runs with no firm, or with the wrong one** (found in the code, not measured; mode b cannot show it).
   * `fill-case.ts`'s start-up recovery (`onModuleInit`, `:185-188`) runs outside every request, so under the walls it finds no `RUNNING` or `QUEUED` copy to recover.
   * Its in-process queue (`enqueue`/`drain`, `:376-381`) runs every queued job in the scope of whichever request started the drain. A second firm's job then cannot see its case (`:385`).
   * The fix: part 3, each job run in its own case's firm (`withFirm`). These are **per-site** changes in the background files.

**What the walls did not break:** with the firm set for case-side requests (mode b), the case-side suites tried all pass, in every area:
* interactive `$transaction`s;
* raw SQL;
* CS-W1's `SECURITY INVOKER` fill triggers, which read the parent case under the wall;
* the case-number counter;
* the checkpoint loader (C10.1 48/48).

**Why the transactions need no edit:** the evidence is PF-12's code and PF-12's own test, not mode b. Mode b gives every connection the firm, so it never exercises the per-request scope (review M3).
* PF-12's `WalledPool` (`api/src/platform/firm-scope.ts`) sets `app.firm_id` and the role on the pooled connection at every checkout, from the caller's async scope. A transaction holds one connection, so it keeps the firm that opened it.
* PF-12's suite proves it on a platform table: `tests/check_pf12_walls.ts:248-249`, "an interactive transaction runs as the firm that opened it". Firms don't leak from one checkout to the next: `:244`.
* `Db` is already that walled client (`core.ts:36`), so the draft's "`Db` subclass" point is settled by PF-12.

**Step 5's re-size:**
* contract today: 2 / 5 / 12 small changes;
* measured: **2 / 3 / 6**.
  * Cause 1 is part 1 (one door).
  * Causes 2 and 3 are part 3: the reset per Sample firm, the background jobs in their case's firm, the start-up recovery. Part 3 carries per-site changes in its own files (`demo.ts`, `fill-case.ts`, and any other in-process queue the census lists under background).
  * Part 2's 100 per-site transaction fix-ups are not needed: no suite failed on a transaction or raw query once a firm was set, and PF-12's test shows why.
  * The high figure keeps room for "Not measured" below.
* **Step 5c** (the audit context and its 25 direct writes) is not in this figure. It moved to AUD-1m's row (draft brief, third point), which waits on AUD-1b (#2124).

## What the spike decides

* **Part 1 is the door.** The firm for `/api/runtime/*`, `/api/link/*` and `/api/demo/*`:
  * staff by `x-actor`: CS-W1's `firmIdByKey`;
  * the simulated client: the case's firm;
  * link sessions: the session's firm.

  On the seam (review m5): Nest middleware runs **before** guards, and PF-4's guard opens the request's scope (`guard.ts:100`, `enterRequest`).
  * A middleware can only tag the request: `setRequestFirm` stores the firm on it (`firm-scope.ts:168-173`). `enterRequest` then reads that tag, as PF-25's host routing does.
  * Otherwise part 1 is a guard or interceptor after PF-4's guard.

  No second `AsyncLocalStorage` and no `Db` factory. The two narrow lookups (`case_firm_of_link_session`, `case_firm_of_case`) stay as the draft says.
* **Part 2 needs no per-site transaction or raw-SQL edits**, on this evidence. It keeps its census lines and its journey-with-walls check per area.
* **Part 3 carries per-site work:**
  * the demo reset (and Reset to the six) must run once per Sample firm, or on a named bypass use. As one firm it cannot finish (cause 2);
  * the in-process queues run each job in its case's firm, and the start-up recovery runs per firm or on a named bypass use (cause 3; `fill-case.ts` first);
  * the checkpoint loader passed as the Sample firm.
* **CS-W2 is unblocked:** the default-plus-trigger fill works under the walls (filing via `case_firm_fill`, party via its default; c72, c76 and csv1 pass in mode b).
