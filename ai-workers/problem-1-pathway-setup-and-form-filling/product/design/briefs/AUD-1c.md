**Points the release Lead confirms in the approval (requirement or code on `main` corrects the row):**
* **No `pgcrypto`.** PostgreSQL 11 and later have a built-in `sha256(bytea)`; the app runs PostgreSQL 18 (`deploy/compose.test.yml`, Homebrew `postgresql@18`) and RDS has it. The trigger uses `sha256(...)`, so no extension is added (no STANDARDS §1 gate, nothing new on RDS).
* **Chaining the existing lines is an `UPDATE`, which AUD-1a's trigger refuses.** The migration disables `aud_event_no_change` for its own back-fill and enables it again before it ends (inside the migration's transaction); a test proves the trigger is enabled afterwards.
* **"`detail` as sorted-key JSON" is not what PostgreSQL prints.** `jsonb::text` orders keys by length, then bytes, and normalises numbers; a TypeScript `JSON.stringify` with sorted keys differs. Write the canonical form **once in SQL** (`aud_event_canonical(line)`, the field list fixed: `chain_key`, `seq`, `id`, `at` as UTC text to the microsecond (`to_char(at at time zone 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US"Z"')`; `canonical.ts` and the verifier read `at` as that text from SQL, never as a JS `Date`, which keeps only milliseconds), `workspace_id`, `firm_id`, `case_id`, `combination_id`, `actor`, `actor_type`, `action`, `entity`, `entity_key`, `summary`, `correlation_id`, `support_session_id`, `detail::text`, each length-prefixed so no two lines collide) and mirror exactly that in `api/src/platform/audit/canonical.ts` (jsonb's key order and number text included); the shared test vector covers keys of different lengths, nested objects, `1.0`, `1e2`, a non-Latin string and nulls.
* **The chain key must follow the demo reset's rule, not only `firm_id`.** AUD-1a lets the reset delete demo-workspace lines, and AUD-1b/AUD-1m will give the Sample firms' case lines a `firm_id`. So: `chain_key` = `sample:<workspace id>` for any line of the demo workspace (whatever its `firm_id`), else the `firm_id`, else `platform`. A reset therefore never cuts a firm's or the platform's chain (P-571 (1)). AUD-4 reads a firm's log by `firm_id`, not by `chain_key` (say so in its card).
* **The incremental checker needs somewhere to keep "last verified".** New table `aud_chain_check` (`chain_key` primary, `verified_seq`, `verified_hash`, `checked_at`, `status` `INTACT | BROKEN`, `failing_from_seq`, `failing_to_seq`) in `audit.prisma`; the row's touch list implies it.
* **The alert kind is `audit.chain_integrity_failure`**, as SA-11-6 names it, ruled (Lead 61, comment 6900882210 on #1870). On `main` the kind is `audit_chain_break` (`ports/alert.ts:11`, raised by nothing yet; used only in `ports/contracts/alert-port.contract.ts:17` and `tests/check_pf23_observability.ts:275`). Part 2 renames it in `ALERT_KINDS` (widening the kind's pattern to allow the dot if it refuses one) and in those two test lines; the shared-contract change is announced in the PR body (P-584).
* **`GET /api/system/audit/integrity` cannot be guarded yet:** `system/audit-log:list` is not in the catalogue and our staff's sign-in (PF-4s) is not on `main`. Part 2 builds the firm route (`agent/audit:read`, in the catalogue since PF-3: OWNER, ADMIN) and the system route's service; the system route's controller lands with PF-4s (or AUD-3, which adds the key as a catalogue data row, P-601 (1)).
* **The per-chain lock is held until commit.** Once AUD-1m passes `tx`, a line written early in a long case transaction holds that firm's chain lock until the transaction ends, so a firm's writers queue behind it, and two transactions that each hold a row the other wants can deadlock (PostgreSQL then fails one; fail-closed rolls it back). Measured in the breaker's run; not a reason to drop the lock (`seq` in commit order needs it).

## Part 1 (AUD-1c-1): the chain columns, the insert trigger and the canonical form (expected ~550 lines)
* **Migration** (audit's file; stamp later than every migration before it and unique; names `aud_event_*` / `aud_chain_*`): `seq` bigint, `prev_hash` and `entry_hash` bytea, `chain_key` text, all `NOT NULL` after the back-fill; unique `(chain_key, seq)`; table `aud_chain_check`.
* **`BEFORE INSERT` trigger `aud_event_zchain`** (PostgreSQL fires same-kind triggers in name order, and `aud_event_chain` would sort before AUD-1a's `aud_event_fill`, hashing a line whose `actor_type` is still empty; the `z` makes it fire last, after every fill): sets `chain_key` (rule above), takes `pg_advisory_xact_lock` on the chain key, reads the head, sets `seq = head + 1`, `prev_hash = head hash` (32 zero bytes for the first), `entry_hash = sha256(prev_hash || convert_to(aud_event_canonical(NEW), 'UTF8'))`. A writer cannot set these columns (any value given is replaced).
* **Back-fill:** existing lines chained once, oldest first (`at`, then `id`), per chain, with the trigger `aud_event_no_change` disabled for this step only.
* **Reset restart:** an `AFTER DELETE` statement trigger (transition table) writes one `chain.restarted` line (actor `system`, Sample) on each `sample:` chain the statement emptied, so `demo.ts` needs no edit; a delete on any other chain is already refused by AUD-1a.
* **`api/src/platform/audit/canonical.ts`:** the TypeScript mirror (pure function, no database), with the shared test vector in the file.
* **Named test cases**, file `tests/check_aud1c_chain.ts` (part 1), a pass and a fail each:
  * **AUD-1c DW1:** 1,000 lines inserted by 20 concurrent writers on one firm give `seq` 1..1,000 with no gap and a valid chain; two firms written at once each have their own gap-free sequence.
  * **AUD-1c DW2:** the TypeScript and SQL canonical forms agree on the shared vector and on 100 random lines read back from the database; a line that differs by one byte in `detail` gives a different hash.
  * **AUD-1c DW3:** after the migration every existing line is chained and valid; a line inserted with no `actor_type` (filled by `aud_event_fill`) and one with microseconds in `at` both verify (their hash covers the filled value: `aud_event_zchain` fires after the fill); `aud_event_no_change` is enabled again (an `UPDATE` is still refused).
  * **AUD-1c DW4:** the demo reset leaves every firm chain and the `platform` chain valid and unchanged, and its `sample:` chain restarts with one `chain.restarted` line; a writer that passes its own `seq` or hash has them replaced.
  * **AUD-1c DW5:** the migration test follows rev 16.7 (measured right after its own migration; never assumes it is the newest); `migrate diff` empty.
* **Touch (part 1):** `prisma/schema/audit.prisma` + one migration folder, new `api/src/platform/audit/canonical.ts`, new `tests/check_aud1c_chain.ts`.

## Part 2 (AUD-1c-2): the checker, its alarm, heartbeat and the integrity read (expected ~500 lines)
* **The checker** (new `api/src/platform/audit/chain/verify.ts`, registered as a `JobPort` recurring job by new `api/src/features/audit-chain.ts`): every 30 minutes from each chain's `verified_seq`, reading only newer lines in pages; weekly, a full pass from `seq` 1. It recomputes each hash with `canonical.ts`, checks `seq` has no gap and `prev_hash` links; on a mismatch or gap it marks the chain `BROKEN` with the range, raises `audit.chain_integrity_failure` with `{ chainKey, fromSeq, toSeq }` only (no summary, no detail, no actor), and does not move `verified_seq` past the break. Each completed pass writes the metric `audit.chain_verify_ok` (PF-23c alarms on its absence).
* **The read:** `GET /api/platform/audit/integrity` (`agent/audit:read`, PF-4's guard) answers the session's firm's chain: last checked at, `INTACT` or the failing range. The system-wide answer is a service function for PF-4s's route (named in the PR body).
