**Fail-closed departs from three requirement ids (P-607 (3), recorded word for word in the PR body):**
* **SA-11-7@2448438c:** "A failed audit write SHALL NOT roll back the user's underlying operation, but SHALL be retried on a durable queue and, if still failing, SHALL raise an integrity alarm (no silent gaps)."
* **SA-11 BR-5** (`SA-11-audit-compliance-and-data-governance_v2.16_2026-10-25.md:624`): "Audit-write failure ≠ business rollback, but ≠ silent. The user's action commits; the audit write retries durably and alarms if it ultimately fails. A gap can never go unnoticed."

What it keeps of the three ids: no silent gap (the alert) and no lost action without a trace (the request fails and is not applied). What it drops: the durable retry queue and "the user's action commits". Unconfirmed: no counsel.

**Points the release Lead confirms in the approval (code on `main` corrects the row):**
* **A retry inside the caller's transaction cannot succeed.** PF-23's `writeAuditWithAlarm` (`api/src/platform/observability/alerts.ts:82`) retries the write up to `AUDIT_ATTEMPTS` times; inside a PostgreSQL transaction the first failed statement aborts the transaction, so every retry fails the same way. The adapter calls it with `attempts: 1` (one try, then the metric line, the error line and the alert, then the error to the caller). No savepoints (Prisma's interactive transactions have none).
* **The alert kind exists already, with another spelling.** `ports/alert.ts:11` has `audit_write_failed` (and `audit_chain_break` for AUD-1c), not `audit.write_failed`. Use the existing kind; do not add a second.
* **The request context exists already.** PF-23's `requestScope` (`api/src/platform/observability/log.ts:28`, set by `requestMiddleware` in `hook.ts:47`) carries `correlationId` (from `X-Request-Id` or new) and a lazy `firmId()` read from `req.platform`; jobs run inside `requestScope` too (`observability/jobs.ts:20`, correlation `job:<id>`) and PF-14's `firmOfJob` (`platform/jobs/pgboss-jobs.ts:55`, `currentJobFirm()`). **Reuse it** (the contract's `AsyncLocalStorage`, §2.5): `RequestScope` gains one optional lazy field `audit?: () => { actor; actorType; supportSessionId? } | undefined`, filled from `req.platform` by the same middleware; no second `AsyncLocalStorage`, and the guard needs no line if `req.platform` already holds the staff id (check `api/src/platform/identity/guard.ts:79-100`; add one line there only if it does not). This puts `api/src/platform/observability/log.ts` and `hook.ts` (PF-23's files, Lead B's) in the touch list instead of the row's "one line in each guard": their OK in the PR.
* **PF-4s (our own staff's sign-in) is not on `main`.** No guard sets `OUR_STAFF` today. Build the context so a guard can set `actorType: "OUR_STAFF"`, test it by entering the scope directly, and leave the PF-4s guard's line to PF-4s's row (name it in the PR body). Same for AUD-3b's `support_session_id` (null until AUD-3b).
* **Keep `detail.firmId` on the line.** `tests/check_pf0p_ports.ts:271`, `tests/check_pf4b_session_reads.ts:218` and `tests/check_pf19a_messages_schema.ts:128` read it. The column is added; `detail.firmId` stays until a later row drops it (so those suites pass unchanged).
* **The three other platform direct writes stay as they are here.** `api/src/platform/identity/audit.ts` (2 lines) and `api/src/platform/settings.ts:133` (1 line) write `audit_event` directly, with actor words such as `user-R` and `detail.from`/`to` values that are whole JSON objects (`check_pf3_platform_schema.ts:185` compares them exactly), which `AuditEntry` refuses.
