**This part (the next part) builds, on the `fake` adapter only:**
1. **Send.** Retainer Send (`POST /api/front-office/retainers/:id/send`, FO-5) creates the signing request in the same step: the adapter's `send` first (the filled version's file), then in Send's transaction one `fo_signature_request` (kind `RETAINER`, the version id, provider `FAKE`, `expires_at` Sample 14 days) and its `fo_signer` rows (each client signer in any order, then exactly one `FIRM` signer = the retainer's representative, last); a failure after the adapter call cancels that envelope (the pattern FO-3c's `send` uses on its branch). A version is sent once (part 1's unique key answers a second send). The one change in `retainers/service.ts` is a call into the new signing service; everything else is new files.
2. **State.** `GET /api/front-office/retainers/:id/signing` (key `agent/retainer:show`, `@OwnOrAll("agent/prospect")` as the retainer read): request status, "1 of 2 signed", each signer's role, name and viewed/signed moments; no token, code or provider id in the answer. Another firm's retainer → 404.
3. **The signed file back.** `POST /api/hooks/signing/:provider` (public, rate limited, no session): the adapter verifies the raw body (unverified → 400, nothing stored); stored once by (provider, provider document id, event id) in `fo_signing_hook_receipt`; `viewed` and `signed` move the signer and the request (CLIENT_SIGNED when every client has signed; a firm signature before every client → refused, state unchanged); `completed` fetches the sealed file and the audit file through the adapter, stores both through `FilesPort`, hashes them into `fo_signing_evidence`, moves the request to SIGNED and the retainer to SIGNED, and emails "Your signed agreement" to each client signer once through `MailPort` (Reply-To the firm's contact address). The request is found by provider document id only (part 1 made it unique across firms, review Major 4). A `CONSULTATION` request is handed to the handler its module registers (a small registry in this part's files); until FO-3c registers `signingEvent`, it is stored and answered 200 "no handler", never applied here. A `declined` event is stored and answered 200 unapplied: **FO-5d** applies it.
4. **`signing.completed`.** One new name `SIGNING_COMPLETED: "signing.completed"` in a new module file `ports/events/signing.ts` (#2919's pattern; plus its one re-export line in `ports/events.ts` if #2919's shape needs one) with its payload schema (rows rev 16.16: document kind, document id and version, signer person ids, document and certificate file keys, sealed sha256; for `RETAINER` also retainer id, prospect id, representative staff id, fee lines, agreed total and currency), written last in the completion's transaction. On it the retainers module makes the prospect WON `E_SIGNED` once (a new file in `retainers/`); a second completion makes none; a consultation agreement makes none.
