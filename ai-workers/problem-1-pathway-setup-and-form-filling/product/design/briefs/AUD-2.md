**Points the release Lead confirms in the approval (requirement, decision or code on `main` corrects the row):**
* **The requirement asks for less than the decision.** SA-11-5@f2081b8e: "The chain head SHALL be **anchored off-site** to an immutable (WORM) store when it has advanced past the last anchor." NFR5-08 (`01-techno-functional/02-Architecture-Decision-Record.md:170-171`): "periodic WORM anchor (S3 Object Lock) of the chain head". **P-571 (3)** widens this to "a daily export of the chain to a write-once store (S3 Object Lock, ca-central-1, compliance mode) with the lock period equal to the longest keep period of row 105". This row builds both: the lines (P-571 (3)) and the head anchor (SA-11-5). No departure.
* **The `sample:` chains are not exported.** AUD-1c's brief makes `chain_key` = `sample:<workspace id>` for every demo-workspace line, which the demo reset deletes (P-571 (1)). Locking them for 7 years would keep Sample lines nobody needs, and every reset would look like a missing range. Export the firm chains and `platform` only; a `sample:` chain is skipped and counted in the run's log line.
* **"A job key per chain and day" does not fit `JobPort`.** `JobOptions.firmId` is a required uuid (`ports/jobs.ts`), and the `platform` chain has no firm; a recurring run has `firmId: null` and sweeps every firm itself. So one recurring run (`audit.archive_export`, daily, Sample 02:15 `America/Toronto`) walks every chain, and the resume rule lives in the archive's own keys (below), not in job keys. A crash mid-run is resumed by the next run (or a rerun) with no duplicate file.
* **"Last export" is read from the archive, not a new table.** The newest anchor of a chain names the last exported `seq`, so `audit.prisma` gets no migration (the series AUD-1a → AUD-1c stays short) and the archive is the one record of what left the database.
* **The anchor comparison is this row's own check, not an edit to AUD-1c's checker.** The row says "the AUD-1c checker also compares". To keep AUD-1c's `chain/verify.ts` untouched, this row registers its own recurring job `audit.archive_anchor_check` every 30 minutes (SA-11-6's cadence) and, on a finding, sets that chain's `aud_chain_check` row to `BROKEN` with the range (data only, AUD-1c's table) and raises the alert. The Lead may instead rule one call line in AUD-1c's checker.
* **The alert kind is `audit_chain_break`** (`ports/alert.ts:11`) with `rule: "SA-11-5"` and `entity: "audit_archive"`; no new kind (the same question as AUD-1c's on the metric name).
* **Retention is AUD-5's constant, counted from the export's own time.** `retainUntil` = the time of the `put` + `KEEP_PERIODS.activity_log` years (7, SA-11-14@78ef59d9: "The whole activity log SHALL be kept 7 years — one number"). An exported line is always newer than its export, so each line is kept at least 7 years. No second constant.
* **The library belongs to the gate's AWS family.** `@aws-sdk/client-s3` at **3.1161.0**, the version of entries 13 and 14, so the three clients share `@aws-sdk/core` and `@smithy/*`; its new transitive packages (S3's checksum and signing middleware) are listed in the entry as entry 13 lists its own, measured with `npm ls`. The gate entry shows P-587's six checks.

## Part 1 (AUD-2-1): the port, the folder adapter, the export and the anchor check (expected ~650 lines)
* **`ports/audit-archive.ts`** (zod only; fake in the same file): `ArchiveKey` (`audit/<chainKey>/<yyyy-mm-dd>-<fromSeq>-<toSeq>.jsonl` or `audit/<chainKey>/anchors/<yyyy-mm-dd>.json`; `chainKey` a uuid or `platform`, never `sample:`); `AuditArchivePort` with `put(key, bytes, retainUntil) → { written: true } | { written: false, reason: "EXISTS" }` (never replaces), `get(key) → bytes | null`, `list(prefix) → key[]` (sorted); **no delete method**. `folderArchive(dir)` in the same file: writes each file once (exclusive create), makes it read-only, refuses an existing key; this is the fake and the local adapter. `ports/contracts/audit-archive-port.contract.ts` (`auditArchivePortContract`), run against `folderArchive` here and against the S3 adapter in part 2.
* **The export** (new `api/src/platform/audit/archive/export.ts`): per chain (firm chains and `platform`), from the newest anchor's `seq` + 1 (1 if none) to the chain's head read at the run's start, in pages; each line as one JSON object (the fields of AUD-1c's canonical list, with `prev_hash` and `entry_hash` in hex) on its own line. Then the anchor: `{ chainKey, date, fromSeq, toSeq, lastEntryHash, fileKey, fileSha256, prevAnchorKey, prevAnchorSha256 }` (anchors chain to each other). **Resume rule:** if the anchor for today exists, the chain is done; if a file starting at `fromSeq` exists with no anchor (a crash between the two puts), its lines are re-read from the database, its hash compared, and only the anchor is written; a mismatch is a finding (below). A chain with no new line writes nothing that day. Exports never mix chains, so a firm's file never holds another firm's line.
* **The anchor check** (new `api/src/platform/audit/archive/anchor-check.ts`): per exported chain, the newest anchor's `toSeq` line in the database has `entry_hash` = `lastEntryHash`; its file exists and hashes to `fileSha256`; weekly, the whole anchor chain back to the first (each `prevAnchorSha256` matches). A finding sets that chain's `aud_chain_check` to `BROKEN` with `{ failing_from_seq, failing_to_seq }` and raises `audit_chain_break` (`rule: "SA-11-5"`, `entity: "audit_archive"`, `firmId` for a firm chain, `count`), ids only; one finding raises one alert (PF-23's repeat window). A completed pass writes the metric `audit.archive_anchor_ok`.
* **Registration** (new `api/src/features/audit-archive.ts`): the two recurring jobs (`audit.archive_export` daily, Sample 02:15 `America/Toronto`; `audit.archive_anchor_check` every 30 minutes) and the adapter choice: `folderArchive` under the OS temp folder when no bucket is configured (local), the S3 adapter in part 2.
