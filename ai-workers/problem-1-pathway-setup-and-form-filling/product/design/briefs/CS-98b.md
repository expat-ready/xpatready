**Where the requirement or the code corrects or narrows the row (the release Lead confirms each in the approval):**
* **The stream is confirmed before the file exists, not after.** **AG-17-5@b7a5e093**: a file is "bound, at creation, to one configurator row — the confirmed stream's row". **AG-17-9@c14292cb**: the file binds "on confirmation". A case on `main` is created on one combination and pinned to its release (`api/src/runtime.ts` `createCase`, `PackWorkPin`). So the proposal is a **read**: `POST …/corporate/stream-proposal` takes location and wage and answers the proposed stream with the threshold, its source and date (AG-17-8). "Open an LMIA file" then takes the job details **and the confirmed stream** in one call, and opens the case on that stream's combination. Choosing a stream other than the proposal records a reason.
* **Change stream must not raise the active count, and it is allowed at the plan limit.** **AG-17-13@ad00f790** and AG17-D47 say so. CS-C1b's count (`api/src/case-count.ts`) counts every case not closed `WITHDRAWN` and not fully decided, so a case closed `STREAM_CHANGED` would still count. This part closes the old file **first**, in the same transaction, and then opens the new one through `createCaseIn`, so the limit check sees N−1. `case-count.ts` gains one condition: a case closed `STREAM_CHANGED` is not active (SA-3-47@4e9b21cd: "Stream changed" ends activity). CS-C1b's brief already notes this outcome as missing.
* **Change stream copies more than the row says.** AG-17-13 copies job details, positions, opening answers and **still-valid employer documents**, and carries the retainer over. The retainer is the front office's (`fo_retainer`, FO-5). This row copies the case-side items and writes no retainer. **Ruled (Lead 61, comment 6901269297 on #1882):** the retainer does **not** carry over automatically. Staff confirm it covers the new file, or start a new retainer version if the scope changes. The new file therefore gets one MAJOR item "Confirm the retainer, or start a new version" that names the old file's retainer (read only), and nothing writes `fo_retainer`. Unconfirmed: no counsel.
* **The file check is AG-17-95's six states, not a warning on confirm.** **AG-17-95@e8aabdd4**: same employer, occupation and work location. (2) An earlier file not yet submitted → "C-… already covers this occupation and location. Add positions to it, or open a separate file anyway." with two choices. (3) Submitted, awaiting decision → information. (4) Approved, still valid, with unfilled positions → a warning with the count and the date. (5) Refused, withdrawn, validity ended or all filled → nothing. (6) Same key, a different stream, not yet submitted → the warning points to Change stream on that file. (7) A file opened by Change stream or Re-apply is not checked against the file it came from. (9) A matching file the user cannot open → "A matching LMIA file exists that you can't open. Ask a manager." One server-side check serves New, Copy and pre-fill. It never blocks (BR-17, rule 10), and "Open a separate file" is audited with the matched file and the user.
* **The prevailing wage is a required field when the table has none.** **AG-17-10@a606b70d**: the table's value → a wage below it is CRITICAL; no value → staff must record the prevailing wage and its source, and **it is not a warning**.
* **The low-wage cap reads workforce figures that do not exist on `main`.** **AG-17-11@7b6313c8** reads them from "the LMIA pre-filing questionnaire (AG17-D33)". `lm.high_wage` has no questions (`samples/wave1.json:60-64`, no sources). This part takes the two figures (total employees, low-wage employees at the location) as job fields in the set-up call, labelled "Sample: until the questionnaire exists". **Ruled (Lead 61, comment 6901269297 on #1882):** the stand-in figures are accepted, labelled Sample.
* **AG-17-3 adds two set-up behaviours.** A missing business number raises a CRITICAL warning when the client's first LMIA file is opened, and never blocks. The business number is read through the front office's company read for the client's `fo_company_id` (Lead B, comment 6901285389 on #1882: no copy in case tables). Until that read has the field, the warning is computed from the port's fake, and the PR says so. A location whose normalised street and postal code match another of the employer's locations offers "This employer already has this location. Use it?" with [Use it] [Add as new].
* **Position changes re-run checks** (**AG-17-87@f7e7aeb5**): each add or remove before submission re-runs the low-wage cap check and the fee estimate, and writes a timeline line. The fee estimate is CS-98d's; this part re-runs the cap check and leaves one call point for the estimate.
* **Warnings use the existing pass record.** CRITICAL needs `agent/case:waive-deficiency` and a reason; MAJOR, MINOR and INFO are acknowledged in one click (AG-17 BR-6). `ReadinessPass` (`review.prisma:74`) stores a pass per filing with a free `code`, so these are passed on the LMIA file's filing with corporate codes. **Step 0:** confirm that opening `lm.high_wage` creates the employer's `Filing` (`api/src/case-prepare.ts:240-256` makes filings from the release's plan; the release has no forms). If it does not, stop and ask: CS-98d's decision (`case_decision` needs a `filing_id` for a `DECISION`) depends on the same answer.
* **`createCase` cannot share a transaction today.** `Runtime.createCase(actor, body)` (`api/src/runtime.ts:241`) takes the simulated `x-actor`, checks it (`need(actor, "case")`, `firmOfActor`) and opens its **own** `$transaction` (`:291`).
