**Where the requirement or the code corrects or narrows the row (the release Lead confirms each in the approval):**
* **Wait for CS-W1; do not use a text firm key.** The row allows "a text firm key until then". CS-W1's brief adds `Case.firm_id` and the composite `(firm_id, id)` key that contract §8 conditions 1-2 need, and CS-W2's pattern (`dbgenerated("nullif(current_setting('app.firm_id', true), '')::uuid")` plus a `BEFORE INSERT` trigger that fills a null `firm_id` from the parent and refuses one that differs) is the one to copy. Born on a text key, these seven tables would need a second migration. Since the LMIA rows are scheduled last, waiting costs nothing. **Note:** nothing sets `app.firm_id` on `main` yet (CS-W2's finding), so the default alone would leave the column null; the parent-fill trigger is what fills it until CS-W3.
* **"Changes `Case` by one slot line only" is not possible in Prisma.** Prisma needs a back-relation field on `Case` for each relation that points at it, and two for `corp_case_link` (from and to). This brief hangs every child off **`corp_job`** (1:1 with the case) instead of the case, so `Case` gains **three** lines (`corpJob`, `corpLinksFrom`, `corpLinksTo`) and `CaseClient` one (`corpLocations`). Those are in `cases.prisma`, the baton file.
* **"Stream changed" needs a value `close_outcome` refuses.** CS-C1a's migration adds `runtime_case_close_outcome_check` with `('WITHDRAWN', 'COMPLETED', 'CLOSED_BY_STAFF')`. AG-17 §6.A and **AG-17-13@ad00f790** close the old file "as 'Stream changed'". This migration **replaces that check with one that also allows `STREAM_CHANGED`** (drop and re-add in one migration). That changes another area's table, so it is outside P-600 (b) ("additive on its own tables only"). **Ruled (Lead 61, comment 6901269297 on #1882):** OK here. It is a migration change, so the Lead reads it before the label (P-423).
* **The requirement has tables the row leaves out.**
  * **AG-17-32@7c77d1f8**: each ad and the job offer are compared with the job details on wage, hours and location, with a `dutiesMatch` tick. AG-17 §7's `ConsistencyCapture` needs a table, so this brief adds **`corp_consistency_capture`**.
  * **AG-17-26@e0210523**: a second channel for one applicant is a note on the one entry (`other_channels_note`), so it goes on `corp_candidate`.
  * **AG-17-41@d07d4284**: the refusal root cause and note. These go on **`corp_job`** (`refusal_root_cause_ref`, `refusal_note`), because `case_decision` (CS-C1a) is insert-only and has no such column.
  * **AG-17-39@7f769295**: positions approved. This goes on `corp_job` (`positions_approved`), because `case_decision` has no count column.
* **AG-17-3@ac1819d0's employer profile: one employer is one `fo_company` row.** The requirement stores the legal name, operating name, business number and registered address "once on the corporate client".
  * **Ruled (Lead 61, comment 6901269297 on #1882):** the master record is the front office's `fo_company`; case-only employer facts stay on the case side, keyed to it.
  * **Ruled (Lead B, comment 6901285389 on #1882):** case-only facts (locations, LMIA files, workers) are keyed to `fo_company.id`. No copy of the company's name or address goes into case tables; they are read through the front office's company read. The case side never writes `fo_company`.
  So this row builds **no** employer profile table. `corp_employer_location` and `corp_job` carry `fo_company_id` (uuid, `NOT NULL`, no foreign key across modules, contract §1 rule 4). `corp_position`'s worker is reached through its job.
  `fo_company` on `main` (`front-office-sales.prisma:314-330`) has `operating_name` only. Legal name, business number and registered address are Lead B's to add behind the company read (Contract gap).
  An LMIA file can open only for a `COMPANY` `case_client` whose `fo_company_id` is set: by FO-8 on `prospect.won`, or by the front office's company door for a direct opening (CS-K1 leaves it null until then).
* **Composite keys need `(firm_id, id)` on each parent, and none may sit under `SET NULL`.** `case_client` has no `@@unique([firmId, id])` in CS-K1's brief, and `Party` gets `firm_id` only in CS-W2 part `cases`. CS-W2's rule (CS-W2.md:40) adds `@@unique([firmId, id])` "when another table points at it". If part `cases` has not added it on `CaseClient` and `Party`, this row adds those two lines in `cases.prisma` (named on the touch list). Under CS-W2's other rule (CS-W2.md:7), `ON DELETE SET NULL` on a composite key would null `firm_id`, which is `NOT NULL`. So **every optional relation** here states its delete rule, and each `SET NULL` one is checked by a `case_firm_match` trigger instead of a composite key:
  * `corp_position.worker_party_id` → `Party`: `SET NULL`, trigger.
  * `corp_position.linked_case_id` → `runtime_case`: `SET NULL` (the demo reset deletes cases), trigger.
  * `corp_candidate.channel_id` → `corp_recruitment_channel`: `SET NULL`, trigger.
  * `corp_consistency_capture.channel_id` → the channel: `CASCADE` (a capture without its ad means nothing), composite key (a null `channel_id` skips the check, `MATCH SIMPLE`).
  * `corp_officer_contact` has no optional parent.
  Every required relation is a composite key with `RESTRICT`, except child → `corp_job` and `corp_job` → case, which are `CASCADE`.
* **`positions approved ≤ requested` across rows is a trigger, not a CHECK.** A CHECK constraint cannot read another row. `corp_job.positions_requested` and `positions_approved` sit on one row, so a CHECK holds there. The rule that `positions_requested` equals the job's count of positions not removed is a `corp_job_positions_count` trigger on `corp_position`, run after insert, delete, and an update of `removed_at` (a removal before submission is an update, not a delete).
