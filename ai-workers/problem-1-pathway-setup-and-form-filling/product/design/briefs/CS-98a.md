**Where the requirement or the code corrects or narrows the row (the release Lead confirms each in the approval):**
* **Wait for CS-W1; do not use a text firm key.** The row allows "a text firm key until then". CS-W1's brief adds `Case.firm_id` and the composite `(firm_id, id)` key that contract §8 conditions 1-2 need, and CS-W2's pattern (`dbgenerated("nullif(current_setting('app.firm_id', true), '')::uuid")` plus a `BEFORE INSERT` trigger that fills a null `firm_id` from the parent and refuses one that differs) is the one to copy. * **"Changes `Case` by one slot line only" is not possible in Prisma.** Prisma needs a back-relation field on `Case` for each relation that points at it, and two for `corp_case_link` (from and to). This brief hangs every child off **`corp_job`** (1:1 with the case) instead of the case, so `Case` gains **three** lines (`corpJob`, `corpLinksFrom`, `corpLinksTo`) and `CaseClient` one (`corpLocations`). Those are in `cases.prisma`, the baton file.
* **"Stream changed" needs a value `close_outcome` refuses.** CS-C1a's migration adds `runtime_case_close_outcome_check` with `('WITHDRAWN', 'COMPLETED', 'CLOSED_BY_STAFF')`. AG-17 §6.A and **AG-17-13@ad00f790** close the old file "as 'Stream changed'". This migration **replaces that check with one that also allows `STREAM_CHANGED`** (drop and re-add in one migration). That changes another area's table, so it is outside P-600 (b) ("additive on its own tables only"). **Question for the tech lead:** OK this one constraint change here (recommended: it is a schema change and this is the schema row), or give it to CS-98b with a `cases` migration of its own.
* **The requirement has tables the row leaves out.**
  * **AG-17-32@7c77d1f8**: each ad and the job offer are compared with the job details on wage, hours and location, with a `dutiesMatch` tick. AG-17 §7's `ConsistencyCapture` needs a table, so this brief adds **`corp_consistency_capture`**.
  * **AG-17-26@e0210523**: a second channel for one applicant is a note on the one entry (`other_channels_note`), so it goes on `corp_candidate`.
  * **AG-17-41@d07d4284**: the refusal root cause and note. These go on **`corp_job`** (`refusal_root_cause_ref`, `refusal_note`), because `case_decision` (CS-C1a) is insert-only and has no such column.
  * **AG-17-39@7f769295**: positions approved. This goes on `corp_job` (`positions_approved`), because `case_decision` has no count column.
* **AG-17-3@ac1819d0's employer profile has no home.** The requirement stores the legal name, operating name, business number and registered address "once on the corporate client". `case_client` (CS-K1) has `display_name` and a `contact` json only, and the company's business facts are the front office's (`fo_company`, FO-8). **Question for the tech lead and Lead B:** (a) a case-side `corp_employer` table, 1:1 with a `COMPANY` `case_client` (recommended: CS-98b's missing-business-number warning and CS-98e's copied facts read it in one place), or (b) read `fo_company` through a port. Until ruled, this brief builds (a) as an optional table in the same file, and the PR says so.
* **`positions approved ≤ requested` across rows is a trigger, not a CHECK.** A CHECK constraint cannot read another row. `corp_job.positions_requested` and `positions_approved` sit on one row, so a CHECK holds there. The rule that `positions_requested` equals the job's count of positions not removed is a `corp_job_positions_count` trigger on `corp_position`, run after insert or delete.
