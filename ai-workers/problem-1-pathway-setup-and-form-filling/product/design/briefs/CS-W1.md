  The plan:
  * **Part 1 never refuses.** Its column is nullable. The fill leaves `firm_id` null while the key has no platform firm, and the backfill fills what resolves.
  * **Part 1 makes the Sample firms exist on every non-production path** through PF-3's own idempotent `seedSampleFirms`, never through SQL in the migration. Production would then carry no Sample rows (P-571 (2)), and `platform_firm` stays Lead B's table. Recommended: `PLATFORM_SAMPLE_SEED=on` in `start.sh`, `tools/isolated.sh` and the CI database set-up, plus one `seedSampleFirms` call at the start of the demo reset and of the checkpoint runner.
  * **Part 2 sets `NOT NULL`**, and refuses in plain words naming the key (PF-3's `unmatchedCaseFirmKeys`, `seed-sample-firms.ts:86`) if a case is still without a firm.
  * **Ruled by Lead 61 (#1872 comment 6900882410, item 11):** `PLATFORM_SAMPLE_SEED=on` goes in `start.sh`, `tools/isolated.sh` and CI's database set-up, and never in a production configuration.
  * **Under PF-12, the seed needs the bypass role.** The demo reset's and `loadConfigured`'s `seedSampleFirms` call writes `platform_firm` and the staff tables for firms other than any one firm, so the `SELECT`-only lookup cannot serve it. It runs through **PF-12's audited bypass role**: the demo reset and the start-up seed go on PF-12's named list (Lead B's OK in the PR).
* **Firm lookups must work under PF-12's walls.** PF-12 forces row-level security on every `platform_*` table except three, so `platform_firm` included. With no firm set, a `SECURITY INVOKER` trigger and any `platformFirm` read by key see no row. That covers this row's fill, CS-C1a's `case_decision` check (`platform_firm` by key, migration line 92) and a staff lookup by `x-actor`. So the key-to-id lookup is **one narrow function**: `case_firm_id_of_key(key text) RETURNS uuid`, `SECURITY DEFINER`, `SET search_path = pg_catalog, public, case_lookup`, `EXECUTE` granted to the app role only. Both the fill trigger and `firmIdByKey` call it as `case_lookup.case_firm_id_of_key(…)`.
  * Because `FORCE` applies to the table owner too, the function is owned from part 1 on by a **dedicated `NOLOGIN` role `xr_case_lookup`** that owns nothing, with `SELECT` on `platform_firm` and a role-only policy `FOR SELECT TO xr_case_lookup USING (true)` on it. If the migration role owned it, the lookup would return nothing from PF-12's merge on, and part 2 could not run. A policy added before row-level security is enabled is harmless, and it holds once PF-12 forces it. The migration role is a member of `xr_case_lookup`; the app role is not.
  * **Ruled by Lead B, PF-12's owner (#1872 comment 6900931491; PF-12's brief rev 16.34):** PF-12 creates `xr_case_lookup` `NOLOGIN` if it does not exist. Until PF-12 merges, the case side creates it the same way, in **this row's part 1**. Whichever lands first creates it and the other is a no-op; from then on the role is PF-12's. The role owns only the three firm-lookup definer functions (this row's `case_firm_id_of_key`, CS-W3's two) and gets no table grant. CS-W3's suite and PF-12's each check that it cannot log in and owns no table. (Replaces Lead 61's interim item 10, comment 6900882410.) **Question for the tech lead (for Lead B):** Lead B's ruling gives the role "no table grant", but a definer function runs with its owner's rights, so these functions cannot read without one. Is a column-level `SELECT` on exactly the columns each function reads the one allowed exception (`platform_firm (id, key)`; `person_link_session (token_hash, firm_id)`; `runtime_case (id, firm_id)`)? This brief assumes yes.
* **No Prisma relation to `PlatformFirm`.** A relation would need back-relation lines in `platform.prisma`, which is Lead B's file with no case-side slot (P-600 (1)(b)), and a foreign key in SQL only would make `migrate diff` non-empty. So, as CS-C1a does for `case_decision.firm_id` (no foreign key; a trigger checks it), `firm_id` is a plain uuid. The fill trigger refuses a `firm_id` the lookup does not return for the key, and the lookup refuses an id that is not a platform firm.
* **Rows that wrote the firm "by key until CS-W1"** switch to `Case.firm_id`: CS-C1a's `case-close.ts:71` (`platformFirm.findUnique({ where: { key: c.firmKey } })`), and CS-K1's and CS-NT1's same lookup if they are merged by then. Each is a one-line change. List them in the PR.
* **The generic fill function for CS-W2 is born here**, so that CS-W2's per-file PRs can run in parallel and none of them owns a shared function: `case_firm_fill()` (`SECURITY INVOKER`; it fills `NEW.firm_id` from the row's parent when null and refuses a value that differs from the parent's).
