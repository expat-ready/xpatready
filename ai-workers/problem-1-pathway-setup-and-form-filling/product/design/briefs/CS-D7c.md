**Points the release Lead confirms in the approval (the requirement and the code correct the row's text):**
* **The type default seeds the flag; it does not decide the translation line.** AG-9-64@645f30f2 §2: "Translation depends on the language of the specific document, not on the document type, so the type default (§3.3) cannot decide it", and rule 12: a type that never needs translation (a photograph) still asks a language only if it carries text. So `translation_default` is the starting value of a document's translation flag and says whether the language question is asked (`NOT_REQUIRED` = a type with no text, the question is optional); the line is CS-D7's and follows the confirmed language for every type. The row's own column (`REQUIRED_IF_NOT_EN_FR`) is kept as a value; CS-D7's test "a type with no rule adds no line" goes (see CS-D7's brief).
* **Validity belongs to SA-01B's captured dates, in months.** AG-9-12@6771d92f seeds "expiry" defaults; **SA-1B-153@90318a60** says each document type lists the dates it captures (0, 1 or 2; roles ISSUE and EXPIRY, at most one each) and **SA-1B-105@8a9b181a** says a programme's document line may carry `maxAgeMonths` (whole months > 0), replacing the type's own period, and needs a type that captures an ISSUE date. So the row's `has_expiry` (bool) and `max_age_days` (int) become `captures_issue_date` (bool), `captures_expiry_date` (bool) and `max_age_months` (int > 0; publish refuses it on a type without an issue date, SA-1B-105 rule 2). **Question for the tech lead:** (a) confirm the shape; (b) SA-1B-153's link of each date to a library DATE field with a client label, SA-1B-105's per-line `maxAgeMonths` on `DocumentRequirement`, and SA-1B-155's validity check (Advisory while preparing, CRITICAL at submission) have **no row**: sequence them as later parts inside Release 1 (Lead 61's ruling on #1867: shaping never cuts a requirement), name the rows.
* **The governed change on `main` is not `library-items.ts`.** `library-items.ts` is delete, retire and restore. The pattern for changing one attribute of a document type with a second person's approval is `document-providers.ts` (C6.14), `document-sets.ts` (C6.15) and `document-supplies.ts` (C4.5): the author proposes the whole value with a reason, a different person approves it on To review (`decideChange`, never the proposer, P-253), the type gets a draft version at approval, published with the next release that carries it, and a release whose types carry none of it is byte-identical (`engine/snapshot.ts:258`). This row copies that pattern in a new `api/src/document-defaults.ts`; each kind is registered by one line in `library-changes.ts`, `lifecycle.ts` and `review-queue.ts` (as `PROVIDERS_KIND` is).
* **A citation needs page, quote and date** (AGENTS rule 4, P-170): the row's "like `DocumentRequirement`" (`source_quote`, `source_file`) lacks page and read date. Each set value carries `{ source_file, page, quote, read_on }`; a proposal with a set value and no complete citation is refused at proposal and again at publish. Values are read by whoever enters them at IRCC's own pages; this row seeds **no** value for any real type (Sample types may carry Sample values, labelled Sample, for the tests).
* **No screen is in this row.** C6.14 had its panel (`web/src/pages/providers-panel.tsx`); this row is "schema + runtime", so the defaults are proposed through the API until a panel exists. **Question for the tech lead:** add the panel as a part of this row (recommended; the library page beside `providers-panel.tsx`) or leave it to CS-D7's part 2.
