**Points the release Lead confirms in the approval (requirement, decision or code corrects the row):**
* **What waits on the account and what does not.** Everything in part 1 is built and tested now (once PF-8a is merged), as PF-8a's own row does: the bucket construct, the policies, the KMS key and the assertion tests on the synthesised template, run by PF-8a's CI job `deploy-synth` with no AWS credentials. Only the live refusal (deleting a locked object version before its date) needs the account: part 2.
* **Compliance mode is irreversible, so staging must not lock test data for 7 years.** A staging bucket at 7 years would keep every test line until 2033 with no way to remove it, even by AWS (question 4 of the row). **Ruled (Lead 61, comment 6900882697 on #1875):** staging at compliance mode with **1 day** default retention; production keeps the decided period (7 years, P-571 (3), SA-11-14). The bucket default alone is not enough, because AUD-2's adapter sends its own retain-until date on every put: **AUD-2 part 1 builds the cap** (`archiveRetainUntil(environment, now)` in `api/src/platform/audit/archive/retention.ts`, 1 day in `test`, its DW5), and this row's staging default and parity test match it. The assertion tests pin both numbers either way.
* **The retention number is shared without importing app code into the CDK tree.** PF-8a gives `deploy/cdk/` its own `package.json`; the app's `ports/keep-period.ts` imports `zod`, which that tree lacks. So the CDK reads `deploy/cdk/config/audit-archive.json` (`{ "productionRetentionYears": 7, "stagingRetentionDays": … }`), and **one app-side test** (`tests/check_aud2c_retention_parity.ts`) fails when that number differs from `KEEP_PERIODS.activity_log`. That test file is outside `deploy/cdk/**`, which the row's touch list names alone: **ruled (Lead 61, comment 6900882697 on #1875), it may sit there.**
* **A deny on `PutBucketObjectLockConfiguration` is a second lock, not the lock.** In compliance mode the default retention can be lengthened but never shortened, and no one can delete a locked version; the deny stops a later stack change from weakening the default for new objects. The account's root user can still remove a bucket policy, so the deny is defence in depth; the test asserts it, and the PR body says so plainly.
* **The KMS key can defeat the lock.** A key scheduled for deletion makes every archived object unreadable after the waiting period. The key gets `RemovalPolicy.RETAIN`, rotation on, and a key-policy statement denying `kms:ScheduleKeyDeletion` and `kms:DisableKey` to every principal but the account root (break-glass); PF-23c's alarms are asked to watch that call (named, not built here).
* **The task role also needs `s3:PutObjectRetention`.** A `PutObject` that sets its own retain-until date (AUD-2's adapter) is refused without it. The role gets `s3:PutObject`, `s3:PutObjectRetention`, `s3:GetObject`, `s3:ListBucket` on this bucket only, plus `kms:Encrypt`, `kms:Decrypt` and `kms:GenerateDataKey` on its key (an SSE-KMS put needs a data key); an explicit deny on `s3:DeleteObject*`, `s3:BypassGovernanceRetention`, `s3:PutObjectLegalHold` and `s3:PutBucketObjectLockConfiguration`.
* **The lifecycle rule never shortens anything.** Expiry of current versions at the production retention + 1 day and of non-current versions after the same, so S3 removes a version only after its lock ends (S3 refuses an earlier removal in any case).

## Part 1 (AUD-2c-1): the bucket as code, proven by synth (expected ~400 lines)
* **A construct** (new file under `deploy/cdk/lib/`, e.g. `audit-archive.ts`) used by both environment stacks: an S3 bucket created with **Object Lock enabled**, default retention **COMPLIANCE** (production: `productionRetentionYears` from `config/audit-archive.json`; staging as ruled), versioning on, KMS (its own customer key, as above), public access blocked on all four settings, a bucket policy refusing plain HTTP and denying `s3:PutBucketObjectLockConfiguration` to every principal, `RemovalPolicy.RETAIN`, the lifecycle rule above. Region by PF-8a's pin (`ca-central-1`). The construct exposes `grantArchiveWrite(role)` with exactly the permissions above.
* **Wiring:** the bucket's name is passed to the task definition as the plain environment value `PLATFORM_AUDIT_ARCHIVE_BUCKET` (a name, not a secret) and `grantArchiveWrite(taskRole)` is called: one line each in PF-8b's stack if PF-8b is on `main`; otherwise the construct ships and PF-8b's row adds the two lines (named in the PR body).
* **Assertion tests** (new `deploy/cdk/test/audit-archive.test.ts`, run by `deploy-synth` with no credentials), each a pass and a fail:
  * **AUD-2c DW1:** the synthesised bucket has `ObjectLockEnabled: true` and a default retention of mode `COMPLIANCE` with the production number equal to `config/audit-archive.json` (a test stack with `GOVERNANCE`, or with no default retention, fails).
  * **AUD-2c DW2:** the bucket and its key are in `ca-central-1` (PF-8a's region guard passes; a copy of the construct in `us-east-1` fails it).
  * **AUD-2c DW3:** the task role's policy allows put, put-retention, get and list on this bucket only and `kms:Encrypt`, `kms:Decrypt`, `kms:GenerateDataKey` on its key only, and denies every delete and the lock-configuration call; a role given `s3:DeleteObject` on the bucket, or lacking `kms:GenerateDataKey`, fails the test.
  * **AUD-2c DW4:** public access is blocked on all four settings, plain HTTP is refused, versioning is on, the bucket and key are retained on stack deletion, the key denies `kms:ScheduleKeyDeletion` and `kms:DisableKey`.
  * **AUD-2c DW5:** the lifecycle rule's expiry is later than the retention period (a rule at 30 days fails).
* **The parity test:** new `tests/check_aud2c_retention_parity.ts` (app side): `config/audit-archive.json`'s production number equals `KEEP_PERIODS.activity_log` and its staging number equals AUD-2's `ARCHIVE_RETENTION_CAP_DAYS`; a changed JSON fails it.
* **Touch (part 1):** new `deploy/cdk/lib/audit-archive.ts` (or the folder PF-8a uses for constructs), new `deploy/cdk/config/audit-archive.json`, new `deploy/cdk/test/audit-archive.test.ts`, PF-8a's environment stacks (one line each: the construct), PF-8b's stack (the two wiring lines, if merged), `deploy/cdk/README.md` (one paragraph: what the lock means and that it cannot be undone), new `tests/check_aud2c_retention_parity.ts` (ruled, Lead 61, comment 6900882697 on #1875).
