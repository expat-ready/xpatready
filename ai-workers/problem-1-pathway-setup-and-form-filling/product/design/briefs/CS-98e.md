**Where the requirement or the code corrects or narrows the row (the release Lead confirms each in the approval):**
* **The real file must keep `linkedOf` working.** On `main`, a worker's link to an employer case is the `RELIED_ON` audit event (`api/src/employer-cases.ts`, tech lead's ruling on #1051, Q3). `api/src/runtime.ts:347` and `api/src/employer-link.ts:69, 88` read it through `linkedOf`. "Create work permit case" therefore writes **both** records:
  * `corp_case_link` `WORKER_PERMIT` (CS-98a), the new record;
  * the same `RELIED_ON` audit event with `Linked`'s fields (`kind: "worker_permit"`), so every existing reader works unchanged.
* **`employerCasesOf` is synchronous over a JSON file.** To read real files it must become async with the database, which changes its two callers in `api/src/employer-link.ts` (`:66`, `:79`). So the hook is **two files**, not one line. Contract v0.1 §7 lists the one-line hooks the release Lead may OK, and `employer-cases.ts` is not among them. **The release Lead's OK is needed for both files** (the row says so for one).
* **Which facts move is the existing rule, fed from the real file.** `carriedFacts(snapshot, employerCase)` (`engine/runtime/employer.ts`) copies only the facts the worker's pinned release reads and asks, never a person's own fact, and blank stays blank. `factState` gives new, same or different, and a different value is never overwritten silently (BR-4 of C1.3). This row builds an `EmployerCase` (`{ key, firm, label, facts }`) from the LMIA file. **Ruled (Lead B, comment 6901285389 on #1882):** one employer is one `fo_company` row, and its name, business number and address are never copied into case tables. So `organisation.employer_name`, `organisation.business_number` and the registered address come from the **front office's company read** for the job's `fo_company_id`, at the moment of the copy. The copy into the worker's answers is the requirement's own "copies, not live links" (BR-11), not a case-table copy of the company. Until that read exists, its fake supplies them in tests and the PR says so. The mapping from the file's fields to library fact keys (`organisation.employer_name`, `organisation.employer_address`, `organisation.business_number`, `case.lmia_or_offer_number`, as `samples/employer-cases.json` uses) is **data**, in a new `samples/corporate-employer-facts.json`, never code (AG-17-6, B164). The map also carries the rest of what **AG-17-45@5cf1e92b** names:
  * occupation (`corp_job` occupation code and its label);
  * wage (hourly wage);
  * work location (`corp_employer_location`'s address);
  * the LMIA number (`corp_job.decision_reference`, ruled above);
  * the decision date (`case_decision.decided_on`).
  Each goes to the fact key the worker's release uses for it. Where no Sample release reads that fact, `carriedFacts` leaves it out (only facts the release reads move), and the PR lists which of the six facts reach the Sample worker combination.
* **Where the LMIA number comes from.** **AG-17-45@5cf1e92b** carries "the LMIA number and decision date". The decision record (AG-17-39, CS-98d) has a date and a letter but no number. The submission record has `application_number` (`FilingRecord`, AG-17-36). **Ruled (Lead 61, comment 6901269470 on #1883):** the LMIA number is ESDC's number on the decision, not the application or file number. Both are kept: `FilingRecord.application_number`, and `corp_job.decision_reference` (CS-98a), which CS-98d records. The map carries `decision_reference`. Any label naming it on screen is cited from the canada.ca page before it is shown, else marked Sample.
* **Shareable documents are a list, not a flag on `DocumentType`.** **AG-17-46@bb7a80df** copies only documents of shareable types. `DocumentType` (`library.prisma:196-223`) has no such flag. CS-98r's `SHAREABLE_DOCUMENT_TYPE` list holds them, released with the pinned snapshot. A later version of a shared document is **offered** to the worker case's owner, never pushed (AG-17-46, BR-11). The offer is part 2.
* **Bill to has no field on `main`.** **AG-17-47@b498c1cf** defaults the worker case's Bill to to the worker, with the employer as a quick pick. The case side has no Bill to; invoices name their party in client money (FO-7b). **Ruled (Lead 61, comment 6901269470 on #1883):** Bill to lives on client money's invoice party (FO-7). The worker's own invoices default to the worker there. This row builds nothing for it, and the PR says so.
* **A lapse needs a cited validity end.** **AG-17-50@fcc346cc**: a CRITICAL at the lead time before validity ends, and `LAPSED` when validity ends with no permit application. P-412 F13 (b) forbids reminders on a worked-out Sample date. An automatic status change on a Sample date would be worse. So with a Sample validity row: no reminder, no automatic lapse, the end date shown "Sample", and staff can mark `LAPSED` by hand. **Ruled (Lead 61, comment 6901269470 on #1883):** no automatic lapse while validity is Sample.
* **The worker case is an individual case and counts as one** (AG-17 BR-14, SA-3-4): it opens through CS-98b's `createCaseIn(tx, opener, …)` on an Individual combination, inside the same transaction as the link and the copies, so CS-C1b's limit check applies to the **individual** metric. The worker becomes a person client (CS-K1). People stay per case (P-588 (2)): the position's worker `Party` and the new case's principal are two records for one person, and the link joins them.
* **Removal and drop-out** (**AG-17-51@1261e68d**). Removing a worker from an approved position returns it to `APPROVED`, history kept. A refused permit is recorded as a milestone, then "worker drops out": the position returns to `APPROVED` while the LMIA is valid, otherwise `LAPSED`.
