## Why
* `api/src/features/case-deadlines.ts:24` registers nothing until a `NotificationPort` is bound to `CASE_DEADLINE_NOTIFICATIONS`. Nothing on main binds it, so the app arms no reminder. Its log says `case_deadlines_waiting` once.
* The port is on main: PF-18np's `ports/notifications.ts`, with `notify(tx, { staffId }, kind, { kind, id })` and its fake and contract.
* The real adapter, PF-18n (BACKLOG row PF-18n), is not built. The preference check is on main as PF-18a part 2's `NotificationPrefsPort`, provided as `NOTIFICATION_PREFS` in `features/platform-settings-personal.ts`.
* One binding covers both reminder kinds, `CASE_STAGE_DEADLINE` (CS-DL1) and `CASE_MILESTONE_DEADLINE` (CS-DL3 part 1, already on main): both go through `case-deadlines/reminders.ts`.

## Build
1. **Table** `msg_notification` in `prisma/schema/platform-messages.prisma` (its comment line 16 reserves it), plus one migration:
   * Columns: firm, recipient staff, kind, group, item kind, item id, created at, read at.
   * Unique on (firm, recipient, item kind, item id, kind): one per person per item and kind (AG-7-39 r2).
   * Firm and recipient as RESTRICT foreign keys to `platform_firm` and `platform_staff(firm_id, id)`, the PF-18bk pattern. Insert and update only; no delete except the 90-day job in part 2.
2. **Adapter** `api/src/platform/notifications/store.ts`, a `PrismaNotificationPort` implementing `NotificationPort`:
   * It runs inside the caller's `tx`, so a rollback leaves no row.
   * It asks `NotificationPrefsPort.allows(staff, NOTIFICATION_GROUP[kind], "IN_APP")` first. Off means no row; a security group ignores the switch (PF-18a).
   * **A repeat for the same item and kind** (the 7-day, 2-day and on-the-day reminders of one deadline) **does not add a row. It marks the existing row unread again and moves `created_at` to now** ("duplicate beats a miss", AG16-60). So there is still one row per item, and it surfaces again.
   * Ids only, no free text (AG-7-39 r10). The link is built when the row is read, never stored.
3. **Binding** in a new `api/src/features/platform-notifications.ts`:
   * Provide `NOTIFICATION_PORT` (the adapter).
   * Provide `{ provide: CASE_DEADLINE_NOTIFICATIONS, useExisting: NOTIFICATION_PORT }`, importing only the constant from `features/case-deadlines.ts`. **Do not edit any case-side file.**
4. **Routes** in `api/src/platform/notifications/routes.ts`, each scoped to the signed-in staff member and their firm:
   * `GET /api/platform/me/notifications/items` (newest first, paged, `?unread=1`)
   * `GET …/unread-count`
   * `POST …/:id/read`
   * `POST …/read-all`
   * Each row comes back with `{ kind, group, item: { kind, id }, link, createdAt, readAt }`. The link for item kinds `case-stage` and `case-milestone` points to that case's page. The Individual/Corporate switch never filters the list (AG-10-36).
5. **Card:** `api/src/platform/MODULE.rows/PF-18n.md` (entry points, table, tests), through the card tool.

**Not this part (part 2, or other rows):** the 90-day removal job; the bell and list screens (PF-18ns); the other callers in row PF-18n (FO-10 and others); the "Needs you" home item (brief **PF-18h**).
