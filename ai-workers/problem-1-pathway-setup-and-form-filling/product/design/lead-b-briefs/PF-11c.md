**What to build, part 1:**
* **The port:** new `ports/firm-purge.ts` (zod only): `FirmPurgePort.register(module, purger)` where `purger(tx, firmId, floors) → Promise<{ module, tablesPurged: { table, rows }[] }>` deletes **only its own module's rows** for the firm; a fake registry and a shared contract `ports/contracts/firm-purge-port.contract.ts` (a test module registers and runs; a purger touching another firm's row or an audit table fails it).
* **Schema:** own area file `prisma/schema/platform-firm-closure.prisma` and one migration folder: `platform_firm_deletion` (firm_id unique, `deleted_at`, `archive_keys` text[], `modules_purged` jsonb (counts only), `backup_expires_at` = `deleted_at` + **35 days** (SA-2-21), `reason`: `PAYMENT_HOLD_90 | CANCEL_90 | CLOSED_LOCK_90`); named `platform_*` for PF-12's `FAMILIES`, with its policy; back-relation lines under a new slot comment in `platform.prisma`. It holds no personal data.
* **The daily job** (`JobPort.recurring`, a time outside 01:00-03:00): finds firms whose clock has run out: `PAYMENT_HOLD` (or cancelled) for 90 days (PF-5's clock) or a closed lock past `closure_due_at` (PF-27). Per firm, in order, stopping at the first gate that fails:
  1. **Legal hold:** `LegalHoldPort.isHeld(tx, firmId, [{ kind: "FIRM" }])` held → nothing removed, the clock **paused** (an audit line `firm.closure_held`), resumes when released (the next run after release).
  2. **The archive copy:** the firm's full export (PF-11's job, the same package) written to the write-once archive through `AuditArchivePort` at `firms/<firmId>/export-<date>.zip`, kept for the longest class in it (`KeepPeriodPort`); **and** the day-0, 30, 60 and 85 notices recorded as sent (PF-5's send records). Missing either → nothing removed, `AlertPort.raise('firm.closure_blocked', …)` once, and the job waits.
  3. **Close:** the firm → `DELETED`; every staff session ended (a `platform_session_revocation` row per staff member) and every client session (through the portal's port once PF-4p exists; until then, staff only, said in the PR); sign-in refused.
  4. **Purge:** each registered purger runs in its own transaction (so one module's failure stops the rest and is retried next run, never half a module), asking `KeepPeriodPort` for floors: a floored class stays in the archive copy, not in the live database.
  5. **Record:** `platform_firm_deletion` written; `platform_firm` row kept (status `DELETED`); **audit lines are never purged** (BR-1, BR-8) and the firm's chain still verifies.
* The job reads across firms, so it names its **`asBypass` use in `BYPASS_USES`** (`firm-scope.ts`) with its reason; each purger then runs inside `withFirm(firmId)`.
* **Restore safety (SA-2-21):** `redeleteAfterRestore()` re-runs the purge for every firm in `platform_firm_deletion` whose `deleted_at` is after the backup's time; PF-8r's runbook (`deploy/RUNBOOK-restore.md`) gains one step that calls it before the system goes live (one line, named in the PR).
* **This part's purger:** the platform's own tables for the firm (staff, roles, settings, consents, messages, templates, complaints, exports, web address), never `platform_firm`, `platform_firm_deletion` or audit tables.
