# Brief note: PF-28, which status an input refusal answers (row owner Lead B; ruling 18 Nov 19:xx IST, rev 17.21)

Asked by Lead 80 after qa-2's re-score (#2136) of R1.10. The front-office routes on `main` answer **422** for field errors (`front-office/sales/common.ts:12`, `public.ts:102-107`: `problem(422, "Check the details", …, { code: "INVALID", fields })`). BACKLOG's PF-28 row says "a refusal answers … with 400", and its sweep expects "400, 404 or 413". The row's text is what's wrong. The code is right.

## The rule (binding for PF-28, the sweep, and every PF/FO row from now on)
| The request | Status | Shape |
|---|---|---|
| The body is not JSON, or cannot be parsed at all (PF-0bp, #2087) | **400** | problem JSON, plain message, the body never echoed |
| The body is too large | **413** | problem JSON (PF-0bp) |
| Parsed, but a field breaks a rule: wrong type, missing, too long, an unknown field under `z.strictObject`, a value not in its list | **422** | problem JSON, `code: "INVALID"`, `fields: { <name>: "<plain words>" }` |
| A path id that is not a uuid, or an id the person may not see | **404** | the same words as any other not found |
| Allowed input, but the state forbids it (stale version, already taken) | **409** | problem JSON with the reason |
| A webhook with a missing or bad signature (contracts §2 item 4) | **400** | it stays 400, because it is a broken request, not a field error |

**Why:** RFC 9110 §15.5.21 defines 422 for content that is understood but cannot be processed, and §15.5.1 defines 400 for a request that is malformed. The screens already read `fields` from 422 to put the words next to each field (EXPERIENCE). Changing working routes to 400 would break them for no gain.

## Changes to PF-28 (BACKLOG text; the tech lead edits BACKLOG)
* (1) "a refusal answers the standard problem shape with 400" → "**with 422 and `fields`** (400 only for an unparseable body, PF-0bp)".
* (3) The sweep's expected set "400, 404 or 413" → "**400, 404, 413 or 422**". An unknown field and a wrong type each expect **422**. A 1 MB string expects **413 or 422**.
* The Done when line "an unknown field on `POST /api/platform/invitations` → 400" → "**→ 422** and nothing stored".
* The webhook amendment (1) stays at 400, for the signature.
* **Existing parts with 400 for a field error** (for example PF-5t part 1's "unknown or old version → 400"; check `git grep -n "problem(400\|BadRequest" api/src/platform api/src/front-office`) are moved to 422 **by PF-28's sweep PR**. Each is listed in the PR with its suite updated. They are not fixed one by one in other rows.
