Claude Ship and our pipeline

Claude Ship gets a pull request ready to merge. It reviews the code, fixes failing checks and conflicts, and applies an approval policy. It does not merge, deploy or test the running app. Of our 11 delivery stages it fully covers 2 and partly covers 3. Our merge queue, our test suites and our qa proof stay.

Is it doing QA verification?
No

None of Claude Ship's pages mention running the app, browser or end-to-end tests, or acceptance criteria. Code Review reads code. PR Steward only fixes checks that are already failing. /ship reviews its own work in the same session.

So Ship can make "merged" faster, but it cannot make anything "Works". That stays with our qa lanes and walks, which are how we got to 64 of 110 rows Works.

Our account switches

How it behaves when you switch accounts every few days

Today: individual accounts, switched at 95% weekly

  • Lost at each switch: cloud builder sessions, the Lead's check and watch, Auto-fix. These belong to one claude.ai account and don't move to another.
  • Not available at all: Code Review, PR Steward and Approvals, which need a Team or Enterprise organisation.
  • /ship and /steward work only on the Mac, never in our cloud builders. A watch ends when a usage limit hits, so it stops right when we switch.
  • Survives: GitHub (branches, pull requests, labels, Mergify) and the repository records. That is why STATE and RESUME carry us over.

With a Claude Team or Enterprise organisation

  • Survives switches: PR Steward, Code Review and Approvals are tied to the organisation and its GitHub App, not to one person's account.
  • Their usage comes from organisation credits, not from the weekly plan we keep running out of.
  • Our GitHub is already Enterprise Cloud, so only the Claude side is missing.
  • Still lost: builder sessions started from a personal account. Building still needs lanes, so the switch routine shrinks but doesn't go away.
Should we simplify?

Yes, in stages 4, 5, 7 and 11. Prove it with a trial before deleting anything.

We have built a lot of machinery around getting a pull request merged. Ship now does part of that job, so we should stop building our own version of those parts and test Ship's against ours.

Your decision

Set up a Claude Team or Enterprise organisation for this repository

It is the only way to get the three agents, and the only way agents survive account switches. Cost: seats plus usage credits, with a spend cap set before PR Steward is turned on (it has none by default). Check whether we qualify for the Enterprise credits by 15 Jan 2027.

48 h trial

Ship against our own flow, on a few lanes

Turn on Code Review and PR Steward, with Approvals in observe mode. Mergify, CI and qa stay as they are. Measure against the week before: Approve-to-merged time, batch failure rate, Lead labels per day, and credits spent. Adopt only if all of these improve and quality does not drop.

After the trial

Retire what Ship replaced, shrink the rules

Remove the label-guard pieces, the review-round tooling and red-PR chasing that Ship covers. Cut RULES down to what Ship doesn't cover. The Lead's job becomes shaping rows, the Lead read for money, schema and migrations, and proof.

Risks to manage
Beta. PR Steward and Approvals are three days old and in public beta.
Merging without a person. Auto-merge plus a Steward push can merge with nobody acting. Keep Mergify's label condition and branch protection, and keep the Claude app off the bypass list.
Approvals is blind to CI. Keep ci as its own required check.
Spend. PR Steward has no limit until we set one. Set a cap per repository first.
Guards skipped. The watch skips git hooks, and it spots secrets by file name only. Our CI guards must keep doing that job.
