# S09 (blind claims, verbatim; model output)

No Blocker or Critical.

M1. Major. api/src/platform/messages/send/messages.ts:99-128 (deliver) and 132-146 (sweep).
- Wrong behaviour: when the channel adapter (or a setting or file read) throws, the row never reaches a final state, and it can hide other rows of the same firm.
- Input and result: `adapter.deliver` throws, which its contract allows ("or throws: not sent"). The transaction rolls back, so the row stays QUEUED with state_reason NULL and no FAILED event. The keyed job dies after pg-boss's 3 retries. The sweep then requeues the row every hour with no attempt limit, no age limit and no failure alert, so a permanently refused message retries forever and a transient failure can go out days late. Also, 50 such old rows of one firm fill its `rn <= 50` "lost" share. Their hour keys are already used, so every later sweep that hour enqueues nothing, and a genuine crash-lost row of that firm (rn 51+) is never picked up while they remain.
- Clause: "a crash after commit sends once"; checklist 7 (a thrown provider error must reach a correct final state) and 12 (no test makes an adapter throw).
- Confidence: 60. IN this change. Today's local adapter itself never throws; reachable now only through a throwing file or setting read.

M2. Major. api/src/platform/messages/send/messages.ts:102, 124-127.
- Wrong behaviour: the provider is called inside the Prisma interactive transaction, before SENT is recorded, with no "sending" mark or provider idempotency token, so a send can happen and then be rolled back.
- Input and result: the adapter accepts the message, then the process dies, or the transaction passes Prisma's default 5 s limit (none is set here), or the following UPDATE or event insert fails. Everything rolls back, the row is QUEUED, and the retry or sweep sends again. The person gets it twice and the first send is not counted in the cap. The firm's counter row is also locked for the whole provider call, so workers of that firm in other processes wait and may time out.
- Clause: "a crash after commit sends once (idempotent job)"; the code's own "sends one outbox row at most once"; checklist 7 and 10.
- Confidence: 45. IN this change (the worker's design). Not visible with the local adapter, which has no outside effect; real with any real adapter.

M3. Major. api/src/front-office/booking/runtime-ports.ts:14 (`mail: fakeMail()`); ports/mail.ts untouched; MESSAGE_PORT (features/platform-messages.ts:17) has no consumer.
- Wrong behaviour: MailPort is not a thin caller of MessagePort, so the running app's booking emails still go to an in-memory fake, outside the outbox, gate, suppression list and cap.
- Input and result: an address on the firm's suppression list books. The confirmation goes through `fakeMail`, with no msg_outbox row, no suppression check, no cap count, and it is absent from the platform inbox. MessagePort cannot yet carry it as is: MailPort sends attachment bytes, MessagePort takes stored file keys only.
- Clause: "One sending path for both sides"; "MailPort … becomes a thin caller of MessagePort with class TRANSACTIONAL"; checklist 2 and 9.
- Confidence: 45 (the row waits on PF-4b, and no MailPort adapter exists in the repo). Left unaddressed beside this change.

- messages.ts:118: the cap's day follows the firm-editable `platform.time_zone`. A trial firm at 50 can switch to a zone already on tomorrow's date and send 50 more at once.
