# S17 (blind claims, verbatim; model output)

Paths: P = web/src/modules/front-office/retainers/retainer-page.tsx, C = .../retainer-card.tsx, S = api/src/front-office/retainers/service.ts. All faults are IN this change.

**M1 | Major | P:171 (with :68, :47-50)**
- Wrong behaviour: "Check and send" ignores unsaved edits on the draft form. It sends the last saved version and throws away what was typed.
- Input and result: draft v2 is saved at CAD 1,500.00. The user types 1750, does not press Save, and presses Check and send, then Send. `changed` is true but is only used to disable Save. POST send goes with v2, so the CAD 1,500 agreement is sent and frozen. `after()` then changes `r`, `reset()` runs, and the typed 1750 disappears with "Version 2 sent." The same happens for a changed signer or representative.
- Clause: "Check before sending"; BR-7/BR-9; checklist 1, 10. Confidence 88.

**M2 | Major | P:114 (with :44, :68)**
- Wrong behaviour: the Representative pick does not include the retainer's current representative once they are no longer eligible, so the page shows someone else as chosen and can dead-end.
- Input and result: the representative is deactivated or loses their licence, and one eligible person, Anna, remains. `reps.data` = [Anna] and `repId` = the old id. A controlled select with no matching value displays its first option, so "Anna" appears selected next to "Edit to choose another". Anna is the only option, so onChange never fires. Save stays disabled, or after another edit it posts the old id and gets 422 "Not eligible to represent". The draft can never be sent. A draft cannot be withdrawn, and the one-live rule blocks preparing another. With several eligible people, the displayed choice is still false.
- Clause: representative choice (BR-3); blocker B-4 "Edit to choose another"; checklist 1, 5. Confidence 85.

**M3 | Major | P:36, :169, :181-184**
- Wrong behaviour: "See the items and how we check" shows the template's newest version, not the version this agreement was made from or frozen with. The `templateChanged` flag the API returns for this is parsed and never used.
- Input and result: a retainer is drafted or sent from template v1 with 5 of 26 items marked, then template v2 marks all 26. The page line says "5 of 26". The panel opened from it says "26 of 26 items marked in this template", with every letter "marked" for this agreement.
- Clause: R1.53 "A draft shows the Code's items, each present or missing"; checklist 8. Confidence 82.

**M4 | Major | P:133 and P:107**
- Wrong behaviour: the page's own fix for a missing value cannot be carried out. Save is `disabled={!changed}`, and `changed` covers only form fields, so "save a new version here" is disabled after the record is corrected.
- Input and result: an Individual prospect whose person has no email. The page says "Add it on X's record, then save a new version here" and links to the prospect page. That page has no email edit, and no front-office route edits a person's email (PATCH people/:id takes phone only). Even if the record changes (email, name, phone), returning shows Save greyed out, because merge values refresh only through a new version. Send stays blocked unless the user makes an unrelated fake edit. The same applies to printing a disclosure recorded after the draft was made.
- Clause: BR-6 blockers with a fix; checklist 1; misleading message. Confidence 80.

**M5 | Major | P:105 (no template control), save payload P:44**
- Wrong behaviour: the retainer page shows the template read-only and never sends `templateId`, although the server's edit supports it. A draft made on an unsuitable template cannot be fixed on screen.
- Input and result: the conflict check is POTENTIAL_CONFLICT and the draft's template lacks {conflict.disclosure}. Send returns 409 "use a template with {conflict.disclosure} and edit the agreement so its new version prints it". Edit offers no template, and a newer file of the same template is not picked up either because edit keeps templateFileKey. A draft cannot be withdrawn, and Prepare answers RETAINER_OPEN, so the prospect is stuck.
- Clause: FO-5s "Prepare retainer sub-page (template, signer, representative, fee rows with When …)"; checklist 1, 5. Confidence 68.

**M6 | Major | S:539 (and :411) with the page's signer Select (P:111) and `after()`/setQueryData (P:37)**

It stays until a refetch (refetchOnWindowFocus is false). The user is told every possible signer lacks the email Send requires.
- Clause: BR-4 / AG-5-50 signer pick; misleading message. Confidence 78.
