## Technology gate record: eslint 10.15.0 with typescript-eslint and react-hooks, report-only
Versions read from registry.npmjs.org on 28 Nov 2026. Each is the newest release published on or before 14 Nov 2026, so every version is at least two weeks old: eslint 10.15.0 (13 Nov), @eslint/js 10.0.1 (6 Feb), typescript-eslint 8.72.2 (9 Nov; peer `typescript >=4.8.4 <6.1.0`, which covers our 6.0.3), eslint-plugin-react-hooks 7.1.1 (17 Apr), globals 17.14.0 (1 Nov). All are pinned exact in the studio's `package.json`, as the file's other dev packages are. The lockfile was written with `npm install --package-lock-only --before=2026-11-14`. It adds 105 packages and moves four existing Babel packages up by patch versions, all published before 14 Nov: @babel/generator 7.29.12 → 7.29.14, its nested @babel/parser 7.29.12 → 7.29.14, @babel/types and @babel/helper-string-parser 7.29.11 → 7.29.14. Without `--before`, npm picked 7.29.15-7.29.16, published 20-27 Nov.

* **Problem.** Lab row LR-083 (FP #76, #101, #213, #214; OS-62) asks for lint. No eslint config is on main, so nothing machine-checks the app's TypeScript or React for unused code, stray `any`, or hook mistakes. The lab register's reason, [C1]: "Give Claude something it can run that comes back pass or fail."
* **Options weighed.** (1) eslint + typescript-eslint + eslint-plugin-react-hooks. The team's stack is TypeScript and React 19, this set is the default lint for that stack, and React's own hook rules ship only as this plugin. (2) Biome: one fast binary, but it has no React Compiler hook rules and is a second toolchain beside tsc and vite. (3) oxlint: fast, but it lacks the hook rules too and its TypeScript coverage is partial. (4) Nothing: keeps the gap. Chosen: (1), without type-aware rules (no `parserOptions.project`). Type-aware rules would make each run slower and tie lint to the tsconfig files.
* **Integration and upkeep.** `prototype/studio/eslint.config.js` (flat config: the recommended sets; `require()` allowed in the CommonJS test scripts; hook rules on `web/src`). `prototype/studio/eslint-suppressions.json` holds the 28 Nov baseline, written by `eslint . --suppress-all` (eslint's bulk suppressions). It holds every error on main when the job landed, as counts per file and rule (999 files). `reportUnusedDisableDirectives` is off, and `react-hooks/exhaustive-deps` is raised to error, because bulk suppressions hold errors only. `.github/workflows/studio-lint.yml` runs `npx eslint .` on PRs that touch the studio. It is report-only (`continue-on-error`, no required check, no Mergify condition) and writes the new findings to the job summary and as annotations. A run takes about 90 s on 4 cores locally. Upkeep: `eslint . --prune-suppressions` after fixes shrinks the baseline. Version bumps go through this gate.
* **The edit-loop hook (LR-083: "hook timed under 2 s per file before it is wired").** Measured 28 Nov with `node_modules/.bin/eslint <file>` (a cold start, three runs each, on a 4-core cloud container): api/src/core.ts (16.7 KB) 0.66-0.71 s; api/src/studio.ts (137 KB) 1.04-1.13 s; web/src/pages/library-forms.tsx (52 KB) 1.78-1.90 s; web/src/runtime/questionnaire.tsx (97 KB) 2.42-2.56 s. The largest React files go over 2 s (the hook rules are the cost), so **the hook is not wired** in this change. Two ways to wire it later, for the tech lead to choose: lint only `.ts` files at edit time, or run the hook through eslint's cache (`--cache`). The Mac's timing may differ. **Wired by LR-181 (28 Nov, cleanup lane).** The cost is one rule: `TIMING=20` on questionnaire.tsx gives react-hooks/static-components 1,966 ms of about 2,080 ms. It is the first React Compiler rule to run, so it pays for compiling the file. `--cache` does not help an edit, because an edited file always misses the cache. So the hook lints with `prototype/studio/eslint.edit.config.js`: this config with the 14 React Compiler rules of eslint-plugin-react-hooks off, and rules-of-hooks, exhaustive-deps and every other rule kept. Timed the same way (cold, three runs, 4 cores, with the bulk suppressions): the 10 largest studio source files 0.77-1.12 s (api/src/studio.ts 134 KB 0.80-0.88 s; web/src/runtime/questionnaire.tsx 94 KB 0.87-1.12 s), the next 5 largest React pages at most 0.84 s. `product/tools/edit-lint.sh` runs it as a PostToolUse hook on Edit, Write and MultiEdit (`.claude/settings.json`). It runs on studio source files only. New findings go to stderr with exit 2, so the agent sees them; nothing is blocked. The compiler rules still run in CI (`studio-lint.yml`, every rule). Test: `product/tools/check-edit-lint.sh` (guards.d/OS-0lr181e.sh).
* **Data and licence.** It reads our source only, with no network at run time. eslint, typescript-eslint, eslint-plugin-react-hooks and globals are MIT; @eslint/js is MIT. They are dev dependencies, run only in CI and by developers. The studio image keeps dev packages today (the Dockerfile: the API runs with tsx, migrations use the prisma CLI), so their files sit in the image but nothing there runs them. MIT asks only that the notice stays with the copies, and node_modules carries each package's licence file (Unconfirmed: no counsel). Cost US$0.
* **When to reconsider.** After 10 report-only runs, a later PR may make the job blocking for new findings (drop `continue-on-error`). Drop the react-hooks rules if they raise more than about one false finding a week. Revisit Biome or oxlint if a run passes 5 minutes.
