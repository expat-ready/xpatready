Plan v3 for the founder · after an independent deep review · 26 Nov 2026

Factory v3: Claude's agents on top of what already works

An independent reviewer (Opus, high effort) checked v2 against the real code on main and against Claude's and GitHub's documentation. Its verdict was adopt with changes. In short: let Claude's agents do reviewing, fixing and approving. Keep Mergify, because it is more capable than GitHub's queue, and drop only the approval label. Cap spend before anything switches on, add the standard security basics, and measure before deleting. Product work never pauses.

Urgent, before anything else (found by Lead 4, 26 Nov)

Your Mac can be reached through the public repository. The Mac's test runner (xr-mac) serves this public repository directly. Anyone outside can open a pull request from a copy of the repository and edit a workflow to run their own code on the Mac. The fix takes one setting, a few minutes, and is your click (repository settings): require approval before workflows run for all outside contributors. Then limit the Mac runner to the one workflow that needs it, or move that workflow to GitHub's own machines. Lead 4 can give you the exact page and button.

Your three decisions
1 · Who approves risky changes?

Every pull request is opened from your GitHub account, and GitHub doesn't count the author as an approver. Today, "the Lead approves" is really the same account approving itself.

Recommended: a separate GitHub account for the Lead (a "machine user"). It approves money, schema, migration and pipeline changes. Your own account keeps an emergency override only.
Alternative: openly accept that Claude approves Claude, with no separate approver.
2 · How much may the agents spend in month one?

We merge about 93 pull requests a day. Code Review has no published price per review. Reviewing every push on every pull request could reach five figures a month.

Recommended: a cap for the first month (for example $1,000). Code Review runs only on risky paths, about 10–15% of pull requests. We measure the real average, then resize.
Alternative: Code Review on every pull request, with a much higher cap.
3 · Which merge queue?

Our Mergify setup runs 4 checks side by side, keeps 40+ areas apart, merges one database-migration area at a time, and uses batches of 2. GitHub's queue is a single line with none of that.

Recommended: keep Mergify. Replace only its "approved" label with GitHub's own approval. That alone retires the whole label-guard family.
Alternative: move to GitHub's queue and accept slower, all-or-nothing batches.

Mature, production-like setup

Basics now; the production layer becomes a hand-over contract

Now: cheap, no slowdown

  • Ruleset on main (above)
  • Dependabot: security fixes plus a weekly grouped update, including our CI actions
  • CodeQL code scanning and secret push protection
  • CI actions pinned to exact versions (commit hashes)
  • CODEOWNERS for pipeline and migration files
  • Approval required before outside contributors' pull requests run CI. Our Mac runner currently serves a public repository, so this matters. Also put the Mac runner in a runner group limited to queue-gate.yml on main, or move that workflow to GitHub's machines.
  • A check that refuses destructive database migrations

At production hand-over (partner team)

  • Staging and production environments with protection rules
  • Deploys without stored passwords (OIDC), and a rollback runbook
  • Restores from backup that are actually tested (the runbook exists; the tests don't)
  • Error alerts and tracing, feature flags, service targets
  • Delivery metrics from GitHub deployments, an incident runbook, access reviews

We write these down as a contract now and don't build them yet, so product work isn't slowed.

    Lead, day 1, half a day

    Everything in the "Now" list.

  4. Shadow run

    Days 1–3

What v2 got wrong (my mistakes, now corrected)
  • Stale numbers. v2 counted an old copy (8 workflows, 98 tool files). The real main has 28 workflows and 298 tool files. The removal list is redone on main before anything is deleted.
  • Replacing Mergify. Our own research said keep it, and v2 dropped it anyway. v3 keeps it.
  • Cost. v2 contradicted itself on seats and ignored volume. v3 uses standard seats, caps first and risky paths only.
  • Approver. v2 assumed "the Lead approves" counts as a second person. It doesn't today, so v3 makes that your decision 1.
  • Delete before measure. v3 measures first, with a go/no-go gate.
